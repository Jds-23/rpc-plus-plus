# Ethereum JSON-RPC Proxy (Rust) (v0.5 — LEAST LATENCY)

Builds on [v0.4-DEDUP.md](v0.4-DEDUP.md). Drilled first in `latency-lab/` on `feat/latency-lab`;
the exercise numbers below (ex1–ex8) point there. Compared against eRPC's selection policy in
[v0.5-LATENCY-erpc.md](v0.5-LATENCY-erpc.md).

## Problem

Spec §3.1 lists least-latency routing first, and §4.1 is its scenario: one of three upstreams
degrades, and the proxy moves new requests to the two faster ones. Neither decider does that.
`ROUND_ROBIN` does not look at the upstreams at all. `PREFER_LEAST_ERRORS` ranks on error rate,
so an upstream that answers every call correctly in two seconds keeps the head. Hedging hides
part of the cost, but every request still waits `hedge_after` on the slow head, and pays for
two calls.

The data is already there. `UpstreamStats` keeps a duration histogram and a duration total
per upstream for the Prometheus collector. What it lacks is a way to tell how long a call
took from how long it took to fail, and any record of the calls the proxy stopped waiting for.

## Goals

- `decider: LEAST_LATENCY`, a third `Decider` beside `prefer_least_errors/`, on the same
  refresher pattern: tick, diff snapshots over a window, score, sort, one `ArcSwap::store`.
- A slow head loses the head within one refresh tick of its slow calls being recorded.
- A head that fails fast does not win the head by failing fast.
- An upstream that is not the head is still measured, so it can take the head when it gets
  faster.
- The ranking holds still on noise: two healthy upstreams a few ms apart do not swap.
- Every attempt is recorded once, including the ones nobody waited for.

## Not doing

- **EWMA scoring.** A time-decayed EWMA (ex7) needs per-call state on the hot path and decays
  only when a sample lands. The window reuses the snapshots already taken and needs neither.
- **Quantile scoring.** p50 from the buckets (ex2) is cheap, but it hides failures and the tail
  better than the mean does. Kept for the dashboard; see *Sharpest decision*.
- **Per-method latency.** `eth_getLogs` and `eth_blockNumber` share one score per upstream. A
  head that serves heavy methods looks slower than it is.
- **A load model.** Nothing compares a loaded head to a loaded challenger (ex6). See *Breaks when*.
- **Tunables in settings.** Same constants-first approach as v0.2; the known gap carries over.
- **Changing `PREFER_LEAST_ERRORS`.** It gets the abandoned-attempt fix for free and otherwise
  stays as it is.

## Interface

### HTTP
No change.

### settings.yaml

```yaml
decider: LEAST_LATENCY   # or PREFER_LEAST_ERRORS / ROUND_ROBIN; default unchanged
```

The failure penalty is the existing `rpc_timeout_in_secs`. Nothing new to configure.

### Metrics

`rpc_attempts_total` gains `outcome="abandoned"`. `rpc_attempt_duration_seconds` now
includes abandoned attempts at the time they were dropped. See *Breaks when*.

## Shape

```
Pipeline::start
  └─ decider.decide(max_attempt)            ── one ArcSwap load + one AtomicU64 add
       ├─ request n % PROBE_EVERY != 0 → ranking, as is
       └─ else → ranking with challenger (n / PROBE_EVERY) % (len-1) + 1 moved to the front
  └─ walk / race / send_once (unchanged)
       └─ try_once
            guard = Attempt::start(observer, id)    ── armed
            call = upstream.call(body).await
            guard.finish(call.record())             ── disarmed, records Ok / Err
            (dropped before finish → Drop records Abandoned at elapsed)

LatencyRefresher (own task, every REFRESH, like RankingRefresher)
  current = observer.snapshot_map()
  window  = current − baseline.front()      ── per upstream, Snapshot::diff
  score   = (answered_micros + faulted × rpc_timeout) / (answered + faulted)
            None if fewer than MIN_WINDOW_SAMPLES calls
  key     = head ? score × PROMOTION_MARGIN : score; unscored last; stable on old order
  ranking.store(sorted); baseline.push_back(current); trim to window
```

Constants, beside `prefer_least_errors`'s: `REFRESH_DEFAULT` 15s, `WINDOW_DEFAULT` 4 ticks,
`MIN_WINDOW_SAMPLES` 20, `PROMOTION_MARGIN` 0.8, and new `PROBE_EVERY` 20.

### Snapshot fields

| field | today | after |
|---|---|---|
| `success`, `unreachable`, `read_failed`, `error_status`, `rpc_error` | counts by class | unchanged |
| `abandoned` | — | dropped before an answer (ex4) |
| `faulted`, `faulted_micros_total` | — | retryable failures (`CallError::is_retryable`), and their time (ex3) |
| `buckets`, `duration_micros_total` | every recorded call | every recorded call, abandoned included |

`Diff` keeps its error-rate methods for `prefer_least_errors`, which count answered calls only:
an abandoned attempt is neither a success nor an error. It gains `latency_score(penalty)`.

## Sharpest decision

**Mean with a failure penalty, not a quantile.** The score is the window's mean, with every
retryable failure counted at `rpc_timeout` instead of its own time (ex3). A 500 in 2ms did
not answer in 2ms: it costs the caller a retry, and the worst case for a retry is the timeout.
A quantile cannot do this. p50 ignores the failing tenth altogether, and ex2 showed p50
ranking an upstream with 5% timeouts ten times better than a steady one. The mean is one
division over two counters already kept. The buckets stay where they are useful, on the
dashboard.

**Only retryable failures pay the penalty.** `execution reverted`, a 400, any 4xx: the
upstream answered, correctly, and every upstream would have said the same (`is_retryable`
already decides this for `walk`). Charging those 3s would let one client's bad payloads demote
the whole fleet, the same unweighted-error bug v0.2 lists.

**Record the attempts nobody waited for.** `try_once` records after `upstream.call(body).await`.
When `race` takes a hedge's answer, when dedup's last caller hangs up, or when axum drops a
disconnected request, the future is dropped at that `.await` and the record line never runs.
The slowest upstream is exactly the one whose calls get dropped, so what is left in its stats
looks fast (ex4: 20 calls, 0 records). An armed guard records `Abandoned` at the elapsed time
on drop. That is a lower bound on the real latency, but it counts. This also fixes the same
blind spot in `prefer_least_errors` and in `rpc_attempt_duration_seconds`.

**Probe inside `decide`, not in `proxy/`.** A slow head never fails, so `walk` never spills
over to #2, and a challenger with no calls scores `None` forever (ex5, and the "tail starves"
entry in v0.2). One request in `PROBE_EVERY` gets the ranking with a challenger moved to the
front, rotating through them deterministically. Probing costs 5% of requests, and hedging caps
the cost of each one: a slow probe is overtaken by the real head after `hedge_after`. The
probe stays in the decider because the proxy should not need to know about rankings, and
`decide` is already called once per request (once per flight with dedup).

**The margin is kept on purpose, and it is not enough.** The head competes at
score × 0.8, as in `prefer_least_errors`, which stops two upstreams 5ms apart from swapping
every tick (ex6: 10 swaps → 0). It does not stop herding. See *Breaks when*.

## Breaks when

- **The head is slow because it is the head.** All traffic goes to the head. If that is what
  makes it slow, a probed challenger measured while idle beats it, takes the head and all the
  traffic, gets slow, and the two swap every tick. The margin cannot stop this (ex6: 10 of 10
  ticks). Fixing it needs either loaded-to-loaded comparison or a traffic split, and neither is
  in this release.
- **Detection waits for completion.** A call is recorded when it answers, fails, or is
  dropped. A head that goes from 20ms to 2s shows up in the window only as its 2s calls finish
  or get overtaken, so add up to `rpc_timeout` to the tick (ex8: degraded at 3.5s, unseated at
  5.5s with 1s ticks).
- **Recovery waits for the window.** A recovered upstream carries its slow calls until they
  leave the 4-tick window, and then has to beat the head by 20%. That can take up to 60s plus
  one tick.
- **Abandoned is a lower bound.** A hedge loser dropped at 150ms records 150ms even if it
  would have taken 2s. Hedging makes the slow upstream look faster than it is, though no
  longer as fast as nothing.
- **Heavy methods skew the score.** The head serves the expensive calls; a challenger probed
  with whatever request number `n % 20` happened to be carries the luck of the draw. With few
  probes per window, one `eth_getLogs` probe can sink a challenger.
- **Probes are paid traffic.** 5% of requests go to an upstream the ranking thinks is worse.
  With hedging off, a probe to a slow upstream takes that upstream's full latency.
- **The dashboard p99 moves.** Abandoned attempts enter `rpc_attempt_duration_seconds` the day
  this ships. Hedged fleets will see their tail grow. It was always there, just never
  recorded.

## Phases

One PR per phase, stacked. Every phase ends green on
`cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`.

### P1 — record retryable failures' time
- `UpstreamStats` / `Snapshot` gain `faulted`, `faulted_micros_total`; `MetricsObserver::record`
  fills them when `CallError::is_retryable()`.
- `Diff` carries `answered_micros`, `faulted`, `faulted_micros`; `Diff::latency_score(penalty)
  -> Option<Duration>` (ex3). Unit tests port ex1 and ex3.
- `✨ feat(observer): split retryable failure time out of duration`

### P2 — record abandoned attempts
- `CallRecord.outcome` gains an abandoned case; `UpstreamStats.abandoned`; collector renders
  `outcome="abandoned"`.
- `try_once`: armed guard around `upstream.call(body).await`, disarmed on finish (ex4). Test: a
  hedge race with a slow primary records the primary as abandoned at the overtake time; a
  completed call records once; a `timeout`-dropped call records the deadline.
- `Diff::error_rate` keeps excluding abandoned; regression test in `prefer_least_errors`.
- `✨ feat(proxy): record dropped attempts as abandoned`

### P3 — least-latency decider
- `src/decider/least_latency/{mod.rs,refresher.rs}`, a copy of `prefer_least_errors/`'s shape:
  `LeastLatency::builder()…spawn()`, same `BuildError`s, `LatencyRefresher::refresh` (ex8).
- `DeciderKind::LeastLatency` (`LEAST_LATENCY`) in `src/config.rs`; arm in `build_decider`
  (`src/app.rs`); `rpc_timeout` passed in as the penalty.
- Refresher tests through the hand-built harness, as in `prefer_least_errors/refresher.rs`:
  ranks on the window; fast failure ranks last; non-retryable errors are not penalised; margin
  holds on jitter (ex6); unscored last in old order; baseline bounded.
- `✨ feat(decider): add least-latency decider`

### P4 — probes
- `LeastLatency::decide` takes a request counter (`AtomicU64`) and moves a challenger to the
  front one call in `PROBE_EVERY` (ex5). Tests: 1000 calls → 950 head, even rotation; fleet of
  one never probes; `max` still caps the chain.
- Integration test in `tests/rpc_proxy.rs`: three wiremock upstreams, one delayed after start,
  `LEAST_LATENCY` with a short refresh → the delayed one stops being first choice (spec §4.1).
- `✨ feat(decider): probe challengers in least-latency`

### P5 — docs
- README decider list; `erpc-comparison.md` and `erpc-gap-priorities.md` row 8.
- `📝 docs: document least-latency decider`

## Known Bugs

### New in this release

- **Probes are invisible.** No log field and no metric say a request was a probe. The only way
  to see probes is a non-head first choice in `attempt_started` with `attempt=1`.
- **Probes bypass the margin's intent.** A probe sends a real user request to an upstream the
  ranking holds worse. That is the cost of measuring it, but it lands on users, not on synthetic
  traffic.
- **The penalty is one number for every method.** `rpc_timeout` is the per-attempt deadline,
  which v0.1 already lists as wrong for heavy methods.
- **The score has no idea of block lag.** A fast upstream several blocks behind wins. eRPC
  scores lag; this does not.
- **Abandoned attempts change an existing metric's meaning** (see *Breaks when*). No new
  family, so old dashboards get the change without being told.
- **Dedup followers do not count.** A flight is one attempt, whatever number of callers waited
  on it; the score weighs calls, not requests.

### Carried forward, still open

From v0.2, still true for this decider: tunables hardcoded; the ranking is global, not
per-client; the ranking is visible only in logs; no capacity or quota model, so a 429 earned
by our own concentration still reads as ill health (it is retryable, so now it also costs the
timeout penalty). The rest unchanged from v0.4.
