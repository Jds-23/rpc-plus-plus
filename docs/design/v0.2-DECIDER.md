# Ethereum JSON-RPC Proxy (Rust) (v0.2)
## Problem
The current state the proxy just has round robin of rpcs. Healthy rpcs have no advantage over unHealthy rpcs, a error out gets same hit as healthy one. Costs us retries count (latency); and no rest period for the RPC (incase of rpc downtime, we keep trashing req).  
## Goals
Create a decider which maintains a ranking of rpcs, the order is based on scoring mechamism of error rate penalty. The rank is recalibrated every 15 secs. 
## Not doing
- Multiple decider logic
- The delisted rpc is not handle the delisted rpc just falls behind in line
- Handling of the tail of the ranking starvation
## Interface
### HTTP
No change in external HTTP
### settings.yaml
```yaml
decider: PREFER_LEAST_ERRORS/ROUND_ROBIN
```

## Sharpest decision

Current decider responds with chain of rpcs in two cases, in one case the in-cache memory is present or valid os the respond is quick and when it as to recalculated it takes extra time. 

In time of 15 secs, the order request go through same endpoints. This is helpful in two ways,
- conseutve req maybe related that helps (Head consistency)
- a certain upstream goes below rank only when it has more than 10% error rate of it's next one, (not without any reason)
- a snapshot diff of 60secs is used to calibrate the ranking  

## Breaks when

- **The window is cold.** The first 60s after boot has no 60s-old snapshot to diff against, so every
  score ties. The order then falls through to whatever `MetricsObserver::snapshots()` hands back,
  which is sorted by label (`src/observer.rs:107`) — a deterministic alphabetical preference that
  looks like a decision and is not one.
- **Offered load exceeds one upstream's capacity.** Concentrating on the best upstream is correct
  while errors are exogenous: an unhealthy endpoint is unhealthy regardless of what we send it, and
  routing away from it converges. A rate limit is not exogenous. A 429 earned by our own
  concentration is a function of the routing decision, so scoring on it is feedback on the loop's
  own output — #1 saturates, demotes, #2 leads and saturates, and the fleet cycles at the window
  period. Below any single upstream's limit this costs nothing. Above it, the proxy manufactures the
  errors it is ranking on, and has no capacity model to tell the two apart. Spreading within a band
  of equally healthy upstreams is what covers this case; ranking alone does not.
- **The tail of the ranking starves.** The chain is `take(min(max_attempt, upstream_count))`
  (`src/proxy.rs:98`), so with more upstreams than attempts the lowest-ranked ones receive no
  traffic, record no samples, and hold their score unchanged forever. Nothing promotes an upstream
  that is never tried.
- **An upstream recovers.** Its bad minute stays inside the diff window until it ages out, so a fully
  healthy upstream keeps its penalty for up to 60s plus the remainder of the current epoch. The same
  window that damps rank churn is what holds a recovered upstream down, and what holds a saturated
  leader in place through an overload episode.
- **Two upstreams sit inside the 10% margin.** The order that wins the first epoch holds
  indefinitely. Because the runner-up is then reached only when the leader fails, it accumulates few
  samples, its error rate stays noisy, and the margin it would have to cross is measured against a
  leader that receives all the traffic.
- **Every upstream is unhealthy.** While `upstream_count <= max_attempt` the ranking reorders the
  chain but never shortens it, so a dead upstream is attempted on every request that gets that far.
  At `rpc_timeout_in_secs: 3` with a `retry_after` sleep between attempts (`src/proxy.rs:107-109`), a
  three-upstream outage still costs about eleven seconds before `retries_exhausted`. Ranking buys a
  better first choice, not a shorter failure path.
- **The process restarts.** Counters start at zero and the snapshot ring is empty, so every deploy
  re-enters the cold window above. There is no persistence, by design.
- **The upstream set changes.** Both the store and the decider are built once at startup, so an
  upstream added to `settings.yaml` needs a restart before it can be scored or served.
- **A configured upstream fails to build.** `build_upstreams` (`src/start_up.rs:88`) drops it and logs
  `upstream_skipped`, while the store keeps an all-zero series for the label. Zero errors out of zero
  calls is indistinguishable from perfect health by ratio alone, so the entry that cannot serve is
  the one a naive score ranks first.
- **A rate limit arrives as a JSON-RPC error on HTTP 200.** `-32005` and its neighbours are counted
  as successes (`src/observer.rs:118`), so the scorer is blind to the throttling case even when the
  provider is explicit about it.
- **The clock is `SystemTime`.** Freshness is `built_at + 15s > now`, and an NTP step either freezes
  the ranking until wall-clock catches up or forces a rebuild on every request. `Instant` is the only
  clock this comparison can be written against.
- **`decider: ROUND_ROBIN` is configured.** The scoring path is inert and none of the above applies.
  The rebuild task is not constructed in that case; the observer still records, because `/metrics`
  depends on it.

## Logging

**No schema change and no new common fields.** The v0.1 schema in [v0.1.md](v0.1.md#logging) stands as
written, and the never-log-`rpc_url` rule extends verbatim: every event below names an upstream by
its `label` alone.

One lifecycle event, emitted before the listener exists and therefore carrying no `request_id`, in
the same class as `startup_ready`:

| Event | Level | Extra fields |
|---|---|---|
| `decider_selected` | info | `decider` — the configured strategy, resolved after defaulting |

Three decider events. These fire on the rebuild task rather than inside a request, so they carry no
`request_id` either — the second class of line in this proxy that legitimately omits it:

| Event | Level | Extra fields |
|---|---|---|
| `ranking_rebuilt` | info | `order` (labels, best first), `scores`, `window_secs`, `duration_us` |
| `ranking_window_incomplete` | warn | `have_secs`, `want_secs` — diffed against a partial window |
| `ranking_upstream_missing` | warn | `upstream` — ranked but absent from the snapshot |

`ranking_rebuilt` is emitted at `info` **only when the order changed**, and at `debug` otherwise. A
rebuild every 15s that always logs is 5,760 lines a day, most of them restating yesterday's order,
and v0.1 already lists uncapped log volume as an Observability bug. The changed-only rule makes the
`info` stream a record of routing decisions rather than of clock ticks.

`ranking_window_incomplete` covers the cold start above. It is a `warn` rather than an `info` because
the ranking it accompanies is arbitrary, and a reader needs to know not to trust it.

One field is added to an existing event: `rank` on `attempt_started` (`src/proxy.rs:148`), the
0-indexed position the upstream held in the chain. Without it, asking whether the ranking helped
means joining every attempt line back to the last `ranking_rebuilt`; with it, first-choice hit rate
is a single filter. The ranking itself is never logged on the request path — that is the volume bug
again, and the rebuild line already holds it.

## Known Bugs

### Closed by this release

- **No health state, so a dead upstream is never removed from the rotation** (v0.1, Routing).
  Partially. The upstream is demoted, not removed, and while `upstream_count <= max_attempt` it is
  still attempted on every request that reaches it. What closes is the first choice; what stays open
  is the tail.
- **Two upstreams share a label** (v0.1.3). Closed by #9 rather than by this release, and recorded
  here because v0.1.3 lists it as live: `validate_settings` rejects both a duplicate label and a
  shared `rpc_url` at startup (`src/settings.rs:120-154`).

### Carried forward, still open

Restated rather than referenced, because a version pointer hides which entries are still live. Full
reasoning stays in [v0.1.md](v0.1.md#known-bugs).

**Correctness** — head divergence across upstreams at different chain heights, now *narrowed* rather
than fixed: a stable order means consecutive requests tend to land on one upstream, which is a
probability improvement that lapses at every rebuild and every failover; no retry classification, so
deterministic errors like `execution reverted` are retried down the ranked chain; JSON-RPC errors
riding on HTTP 200 are undetectable under the status-code-only rule, **and now corrupt the ranking as
well as the metrics**; error responses always carry `id: null`; `eth_sendRawTransaction` retry is
unsafe; batch rejection is a transport-level `[` peek with no JSON-RPC error object.

**Observability** — no JSON-RPC method in logs or metrics, so scoring cannot distinguish a heavy
method from a failing upstream; `duration_ms` excludes the inbound body read; log volume is uncapped
at four lines per request; the log schema is still unasserted.

**Timeouts and limits** — per-attempt timeout is a fixed value and wrong for heavy methods; no total
deadline; no inbound request timeout; no request body size cap; `Retry-After` response headers are
ignored, which is the one signal that would separate a rate limit from ill health; no exponential
backoff.

**Config and naming** — API keys live in YAML; `retry_after` is a misleading name for a flat
inter-attempt delay; a `reqwest::Client` per upstream rather than one shared; `max_attempt` can be
silently unreachable when it exceeds the upstream count, which is also what makes the ranking
order-only rather than membership-changing.

### New in this release

- **The 10% margin is not a transitive comparator.** Defined pairwise against the next upstream, it
  admits A within margin of B, B within margin of C, and A far beyond C. `sort_by` with an
  inconsistent comparator is documented to panic or return an unspecified order, so the margin has to
  be applied against the previous ranking or expressed as score buckets.
- **Hysteresis has no input.** "Goes below rank only when" is a comparison against the previous
  ranking, and the rebuild in *Shape* reads only the observer. The outgoing `Arc<Ranking>` is not fed
  back in.
- **A request-triggered rebuild cannot hold a fixed window.** On the lazy path the snapshot ring
  advances only when a request arrives, so a 60s window silently becomes "the last four rebuilds,
  whenever those happened". The window and the tick task are one decision.
- **No capacity or quota model.** Nothing separates an error the upstream would have produced anyway
  from one this proxy's own concentration caused, so a rate limit reads as ill health. This is the
  bound on the release: rank-by-error-rate is sound while offered load stays under a single
  upstream's limit and becomes a feedback loop above it.
- **The three tunables are hardcoded.** 15s, 60s and 10% appear in no interface, so tuning any of
  them is a recompile.
- **`Settings` has no `decider` field** (`src/settings.rs:13`). It needs a `set_default` alongside the
  existing ones (`src/settings.rs:61-64`) or every current `settings.yaml` fails to load, and a
  `validate_settings` arm or an unrecognised value starts silently on the wrong strategy.
- **The ranking is global, not per-client.** Head consistency and load concentration are the same
  fact seen from two sides; there is no way to take one without the other.
- **Latency is not scored.** An upstream that answers slowly and correctly outranks one that answers
  quickly and fails occasionally, so p99 can worsen while the number this release optimises improves.
- **There is no minimum-sample floor.** One error out of one call reads as a 100% error rate, which
  is enough to demote an upstream for a full window.
- **Error classes are unweighted.** A 429, a 500 and a 400 caused by a malformed client payload all
  count the same, so a single bad client can demote the whole fleet at once.
- **The ranking is externally unobservable.** *Interface* adds no HTTP surface, so `/metrics` exposes
  neither rank nor score and the only view is the log line.
