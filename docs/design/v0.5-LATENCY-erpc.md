# v0.5 LEAST_LATENCY vs eRPC selection policy

Supporting note for [v0.5-LATENCY.md](v0.5-LATENCY.md). eRPC read from `main` on 2026-10-16.

The two designs agree on recording abandoned attempts and on the window. eRPC is stronger on
stability: a 30s minimum between primary switches, and a score with a floor in absolute time.
v0.5's mean with a failure penalty is the more principled latency number and stays.

## Sources

eRPC moved scoring out of `upstream/registry.go`, where `RefreshUpstreamNetworkMethodScores`
is now a no-op, into a JavaScript policy engine under `internal/policy/`.

- [internal/policy/default_policy.js](https://github.com/erpc/erpc/blob/main/internal/policy/default_policy.js): the default chain
- [internal/policy/stdlib/stdlib.js](https://github.com/erpc/erpc/blob/main/internal/policy/stdlib/stdlib.js): `sortByScore`, `stickyPrimary`, `probeExcluded`, presets
- [health/tracker.go](https://github.com/erpc/erpc/blob/main/health/tracker.go): which outcomes feed the latency sketch
- [common/defaults.go](https://github.com/erpc/erpc/blob/main/common/defaults.go): 15s evaluation interval, `network` default scope

The default chain:

```
removeCordoned
→ excludeIf(errorRate > 0.7 | throttleRate > 0.4 | slow | head lag)
→ whenEmpty(all upstreams)
→ preferTag('!tier:fallback')
→ sortByScore(PREFER_FASTEST)
→ stickyPrimary({ hysteresis: 0.30, minSwitchInterval: '30s' })
→ probeExcluded({ sampleRate: 0.1, minSamples: 10, maxConcurrent: 4, timeout: '10s' })
```

## Where they agree

- **Abandoned attempts are a lower bound, not nothing.** eRPC feeds hedge cancels, client
  disconnects and engine timeouts into its latency sketch at the elapsed time, and keeps hedge
  attempts out of its request and error totals. That is P2: an abandoned attempt is neither a
  success nor an error.
- **Window and tick.** eRPC uses a 1-minute rolling window in 10 sub-buckets and re-evaluates
  every 15s. v0.5 uses 4 ticks of 15s.
- **Non-retryable errors are not penalised.** eRPC counts an EVM revert as a normal latency
  sample and ignores `ClientSideException`. v0.5 skips the penalty for anything `is_retryable`
  rejects.

## Where they differ

| Axis | v0.5 `LEAST_LATENCY` | eRPC default policy |
|---|---|---|
| Latency number | Window mean | p70 from a rolling quantile sketch |
| Fast-failure defense | Each retryable failure counted at `rpc_timeout` inside the mean | Hard errors kept out of the sketch; separate `errorRate × 4` term; excluded above 70% errors |
| 429 | Retryable, so it pays the timeout penalty | Own `throttledRate × 4` term, not an error; excluded above 40% |
| Score shape | Pure latency ratio | `1 / (1 + 15·p70_s + 4·errorRate + …)` |
| Stability | Head competes at score × 0.8, every tick | 30% margin on score **and** 30s minimum between primary switches |
| Too few samples | Under 20 → unscored, ranks last | No gate in the sort; all-zero metrics score 1 and rank first |
| Exploration | 1 in 20 real requests reordered to a challenger; the user waits | 10% of real requests copied in the background to excluded upstreams only; quota pays; 4 in flight max; 10s timeout; unsafe methods skipped |
| Hard exclusions | None, ranking only | Errors > 70%, throttles > 40%, p70 > 3s and 3× peers on most methods, p70 > 10s, ≥ 16 blocks or 30s behind; all upstreams if every one is excluded |
| Per-method | One score per upstream | Head picked across methods; slow-exclude compares per-method p70 (geomean or majority, 50 samples min, 30ms damping) |
| Other signals | Latency only | Block head lag, finalization lag, misbehaviour, tier tags, cordon |
| Load and herding | Open, see *Breaks when* | No load model either; the 30s minimum caps the swap rate |
| Tuning | Constants | JS policy per project; presets `PREFER_FASTEST`, `PREFER_FRESHEST`, `PREFER_LEAST_ERRORS` |

`PREFER_FASTEST` weights: latency 15 per second of p70, errors 4, throttles 4, misbehaviour 2,
block lag 1, finalization lag 0.

## Takeaways

1. **A minimum time between switches.** eRPC's source says a margin alone does nothing during
   an incident, because the score gap is huge, so the head flaps every tick. It adds
   `minSwitchInterval: 30s`. In v0.5 that is one `last_switch_at` in the refresher. It does
   not fix herding, but it bounds how often the head can swap.
2. **A floor in absolute time.** v0.5's margin works only on ratios: 5ms against 7ms swaps,
   since 7 × 0.8 = 5.6 > 5. That breaks the goal that upstreams a few ms apart hold still.
   eRPC's `1 +` term acts as a floor of about 67ms, so 20ms against 50ms differs by only 1.35×
   in score. The ex6 jitter test may miss this if its baseline latency is large.
3. **Keep mean plus penalty.** It puts failures in time units: the expected cost of a call.
   eRPC's error term is weak; 100% errors adds as much as 267ms of p70, so its real defense is
   the 70% exclusion. The case against quantiles holds for a quantile alone; eRPC fills that
   gap with a second term.
4. **Background probing is the rejected alternative.** It costs users nothing, but it spends
   upstream quota and needs a filter so write methods are not sent twice. The in-band probe
   sends each request once and keeps the proxy unaware of rankings.
5. **Opposite cold-start choices.** eRPC ranks an upstream with no samples first: optimistic,
   a form of exploration that the 30s minimum dampens. v0.5 ranks it last and relies on probes.

## Open questions

- Does the minimum time between switches ship in v0.5, or go under *Known Bugs*?
- Add the absolute floor, or accept the noise risk at low latencies?
