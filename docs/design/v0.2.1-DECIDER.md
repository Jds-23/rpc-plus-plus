# Ethereum JSON-RPC Proxy (Rust) (v0.2.1 — DECIDER)

Supersedes [v0.2-DECIDER.md](v0.2-DECIDER.md) where the two conflict.

## Problem

v0.2 specifies two rebuild paths that cannot coexist. *Shape* rebuilds inside `decide` on a
freshness check; *Known Bugs* states a request-triggered rebuild cannot hold a fixed window,
because the snapshot ring then advances only when a request arrives. It also leaves the
hysteresis rule undefined — a pairwise margin is not a valid comparator, and v0.2 says so
without naming a replacement.

## Goals

One rebuild path. A hysteresis rule that is a total order. A sample floor, so a single call
cannot set an upstream's rank.

## Not doing

Unchanged from v0.2: multiple deciders, delisting, tail-starvation handling, capacity model.
Latency stays unscored.

## Interface

### HTTP
No change.

### settings.yaml
No change. `decider: PREFER_LEAST_ERRORS` selects this decider.

## Shape

`decide` is a read. Nothing rebuilds on the request path.

```
Req Handler ──decide()──> ArcSwap<Cached> ──take(max)──> chain
                                ^
                                │ store
RankingRefresher — tick task, one tick per `refresh`
  └─ snapshot_map() ─ diff against baseline.front() ─ score ─ sort
     baseline: VecDeque<snapshot>, held at `window_ticks`
```

Each tick diffs the current snapshot against the oldest held one, so the measurement window is
`refresh × window_ticks` of wall clock whatever the traffic. 15s over four ticks is 60s.

## Sharpest decision

**The window belongs to the tick task, not to `decide`.** v0.2 offers "CAS or tick task"
alongside a lazy freshness check; those are exclusive. A lazy rebuild makes a 60s window mean
"the last four rebuilds, whenever those happened" — the window and the tick task are one
decision, and the tick task takes it. `decide` costs one `ArcSwap` load.

**Hysteresis is one scalar per upstream.** The incumbent's error rate is multiplied by the
margin before sorting, so a challenger must beat it by that factor to take the head. The
comparator never sees a pairwise rule and stays a total order; `sort_by` on an inconsistent
one panics.

**The margin applies to the head alone, at 20%.** v0.2 asks for 10% against each upstream's
next one. Positions below the head are reached only when the head fails, so they never gather
the samples a pairwise rule needs. Stabilising the head is the whole of what the rule buys.

**An upstream under the sample floor is not ranked.** An untried upstream's error rate is 0.0,
which beats every measured one. Ranking on that swaps head and challenger every tick, since
the head takes all the traffic and is the only one measured. Below `min_samples` calls in the
window an upstream is unscored, sorts behind every scored one, and keeps its relative position.

Absolute error-rate bands are rejected as the hysteresis rule: 5% buckets put everything under
2.5% into one band, which is where healthy upstreams live, and tie the fleet.

## Breaks when

v0.2's list stands, except:

- **The window is cold.** Ticks before the ring fills diff against the boot snapshot. Logged,
  not silent.
- **The tail starves.** Narrowed — a starved upstream holds position rather than being promoted
  on a false 0.0. It still receives no traffic.

Added by the rules above:

- **The runner-up is unmeasurable while the head is healthy.** It stays under the floor, so it
  is promoted only once the head degrades enough to spill traffic down the chain.
- **Low volume freezes the order.** Under `min_samples` per window every upstream is unscored
  and the ranking holds at config order.
- **The floor and the margin are single values.** Neither adapts to request rate.

## Logging

v0.2's table stands, minus one row.

`ranking_upstream_missing` is dropped. `spawn` refuses an upstream the observer does not track,
and the observer's key set is fixed at construction, so the event cannot fire. The startup
error carries that case.

## Known Bugs

### Resolved from v0.2

`The 10% margin is not a transitive comparator`, `Hysteresis has no input`, `A
request-triggered rebuild cannot hold a fixed window`, and `There is no minimum-sample floor`
are answered by *Sharpest decision*.

### New in this release

- The margin's value and its head-only scope are asserted, not measured. No traffic stands
  behind either number.
- Unscored is sticky in one direction: a fleet-wide quiet period pins the order.

### Carried forward, still open

Unchanged from v0.2, except that JSON-RPC errors arriving on HTTP 200 and counting as
successes is now the largest error in the ranking's input, not only in `/metrics`.
