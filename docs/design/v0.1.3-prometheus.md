# Ethereum JSON-RPC Proxy (Rust) (v0.1.3 — prometheus)

## Problem

v0.1.2 built the observation seam and wired it to a sink that throws everything away. Every
attempt already produces a `CallResult` carrying duration and a typed outcome
(`src/upstream.rs:110`), narrows to a borrowed `CallRecord` (`src/upstream.rs:127`), and is handed
to an `Observer` keyed by `UpstreamId` (`src/observer.rs:3`) on every attempt
(`src/proxy.rs:154`). The only impl is `NoopObserver`, which binds both arguments to `_` and
returns (`src/observer.rs:16-21`), and that is what `main` constructs (`src/main.rs:11`).

So the proxy measures itself and then discards the measurement. Three separate pieces of work are
blocked behind that single missing impl, which is why this release exists before any of them:

- **There is no fleet-level view.** Per-request logs describe one request; nothing answers "which
  upstream is failing right now" without grepping. Listed as an Observability bug in v0.1 and
  restated in v0.1.2.
- **v0.2's health scoring has nothing to score.** The background clock in
  [draft/v0.2.md](draft/v0.2.md) snapshots a metrics db that does not exist. The scoring loop is
  the only consumer that makes the routing work possible, and it needs a store it can read, not a
  log stream it would have to parse.
- **There is no baseline to load test against.** Throughput and p99 numbers require the proxy to
  report its own attempt latencies; measuring only from the client conflates proxy overhead with
  upstream latency.

Tracked as **#7**, whose first half is this release. #7's second half — an injectable log writer
so the schema can be asserted — is deliberately split out; see *Not doing*. This should land before the
#9 (settings validation), no huge resaon. This would currently run in local, so settings can be validated.

## Goals

- **Every attempt outcome lands somewhere readable**: the `CallRecord` already constructed on the
  hot path is folded into a per-upstream store instead of being dropped, at a cost the hot path
  can absorb.
- **`GET /metrics` exports what Prometheus needs and nothing more**: raw counters and histogram
  buckets, so the rate arithmetic happens in PromQL rather than in the proxy.
- **The store v0.2's clock will snapshot is the store this release builds**: one structure, two
  readers. No second source of truth appears in v0.2.

## Not doing

Carried forward from v0.1 and v0.1.2: caching, least-latency routing, auth, batch handling (still
HTTP 400), multichain, in-flight dedup, hedging.

New to this release, and deferred on purpose:

- **Health scoring, bands, exclusion lists, `ArcSwap<Plan>`**: this release fills the store; v0.2
  reads it. No `Decider` impl is added and `src/decider.rs:10` is untouched.
- **Docker, compose, Prometheus and Grafana as deployed things**: the proxy exposes an endpoint. A
  scraper and a dashboard pointing at it are the next release's subject.
- **Injectable log writer (#7's second half)**: `telemetry::init` still takes no arguments and
  still writes to stdout, so the log schema remains unasserted for one more release.
- **Body parsing**: raw passthrough holds. No `method`, no `id`, no `finality` — which is why
  every metric here is keyed by upstream alone, exactly as the observation sink already is.
- **Request-level metrics beyond a total**: the retry loop knows attempts; wiring a request-scoped
  histogram touches `proxy_inner` rather than the observer.

- **#7's log-writer half** — the release that adds a new export surface still cannot prove its log

## Interface

**The first interface delta since v0.1.** v0.1.2 deliberately shipped none; this release adds one
route and no configuration.

### HTTP

| Method | Path | Purpose | Auth |
|---|---|---|---|
| GET | `/metrics` | Prometheus text exposition of per-upstream attempt counters and latency buckets | None |

Registered alongside the existing two in `build_router` (`src/route/mod.rs:16-21`).

### settings.yaml

Unchanged. `application_host` landed separately and is the key that makes `/metrics` reachable
from outside the container — and, for the same reason, the key that exposes it. See *Breaks when*.

### Metrics

Counters and histograms only. No gauge carries a rate, no metric is precomputed — this is the
correction #7 makes to [draft/v0.2.md](draft/v0.2.md)'s interface table, which specified
"error rate, success rate" as exported values.

| Metric | Type | Labels | Notes |
|---|---|---|---|
| `rpc_attempts_total` | counter | `upstream`, `outcome` | `outcome` ∈ `success`, `unreachable`, `read_failed`, `error_status` — one variant per `CallError` (`src/upstream.rs:139`) plus success |
| `rpc_attempt_duration_seconds` | histogram | `upstream` | from `CallRecord::duration` (`src/upstream.rs:128`) |

Seconds, not milliseconds, because Prometheus convention is base units: `histogram_quantile` returns
whatever the bucket bounds are in, and a dashboard that has to remember this one histogram is in
milliseconds will eventually forget. The store keeps microseconds as `u64` — there is no
`AtomicF64` — and divides once per scrape rather than once per attempt.

Bucket boundaries, in seconds:

```
0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 3.0, 5.0
```

Dense below 250ms, where a healthy upstream lives and where the difference between providers is
worth seeing. `3.0` is `DEFAULT_RPC_TIMEOUT_IN_SECS` (`src/upstream.rs:10`): the timeout needs a
boundary of its own, because a timeout that lands in `+Inf` says only "slow" when the interesting
fact is "hit the ceiling". `5.0` catches a timeout that fires late. `+Inf` should stay near-empty,
so a filling `+Inf` means `rpc_timeout_in_secs` has been widened and these boundaries no longer
straddle it.

**No label may carry a URL.** The never-log-`rpc_url` rule extends verbatim to metric labels:
`upstream` is the `UpstreamId` newtype (`src/upstream.rs:13`), which is built from the configured
label and never from the URL. A scrape endpoint is more exposed than a log file, so the rule is
stricter here, not looser.

## Shape

```
 Req Handler ──> retry loop ──> Upstream::call ──> CallResult { duration, result }
                                                        │
                                                        │ .record()  (src/upstream.rs:116)
                                        `                v
                                              CallRecord { duration,
                                                           outcome: Ok(StatusCode)
                                                                  | Err(&CallError) }
                                                        │
                                                        │ observer.record(&UpstreamId, ..)
                                                        v
                        +-----------------------------------------------------+
                        | MetricsObserver                                     |
                        |   HashMap<UpstreamId, Arc<UpstreamStats>>           |
                        |   built once at startup, never mutated              |
                        |                                                     |
                        |   UpstreamStats { AtomicU64 counters + buckets }    |
                        +-----------------------------------------------------+
                              ^                              ^
                              │ reads                        │ reads
                              │                              │
                   GET /metrics (this release)      v0.2 scoring clock (later)
```

The map is sized and populated from the upstream set at construction, so lookup is a read of an
immutable structure and the only write on the hot path is a relaxed `fetch_add`. No `RwLock`, no
entry insertion, no allocation per attempt.

Fixed rather than concurrent because `Observer::record` takes `&self` (`src/observer.rs:4`) and an
atomic only works while nothing moves it: a `HashMap` that can insert will rehash, a `Vec` that can
grow will reallocate, and either invalidates the address the counter lives at. So "populated once"
and "relaxed `fetch_add`" are one decision stated twice — reach for a concurrent map and the
lock-free hot path goes with it.

The store also holds no time dimension. Each reader brings its own window: `/metrics` leaves it to
PromQL's `rate()`, and v0.2's clock diffs consecutive snapshots against wall-clock elapsed. A store
keyed by time window would compute the same rates a second way, and would be the only thing forcing
a lock. What it costs is *Breaks when*'s last two entries: no upstream can be added without a
restart, and a label not present at startup has nowhere to record.

## Sharpest decision

**The store is the source of truth; Prometheus is a view over it — not the other way round.**

The obvious implementation registers Prometheus counters and calls `.inc()` on them, letting the
registry own the numbers. That works for exactly as long as the only reader is a scrape. v0.2 adds
a second reader with different needs: the scoring clock wakes every `snapshot_period`, reads every
upstream's counters, diffs them against the previous snapshot, and sorts the result into bands. A
registry is a write-mostly API — reading values back out of one to make routing decisions is the
tail wagging the dog, and it coloured the whole design.

So `UpstreamStats` is a plain struct of `AtomicU64`s that this release owns, and the `prometheus`
crate is used only to render it on demand at `/metrics`.

That is also what settles the library choice. `metrics` + `metrics-exporter-prometheus` is the
more ergonomic facade, but the facade owns the data — recovering per-upstream numbers to score
against means going through the exporter, which is the exact coupling this decision refuses. Raw
`prometheus` is used as an exporter *over* our own structure, which keeps the read path direct.

That is also why `CounterVec` and `HistogramVec` go unused, even though they are the crate's
ergonomic path: both put the numbers inside the registry. What is used instead is the `Collector`
trait — `MetricsCollector` (`src/route/metrics.rs`) holds an `Arc<MetricsObserver>`, and
`Registry::gather` calls into it at scrape time. The registry holds two `Desc`s and no values.

```rust
// src/observer.rs — the store

pub struct UpstreamStats {
    success:      AtomicU64,
    unreachable:  AtomicU64,
    read_failed:  AtomicU64,
    error_status: AtomicU64,

    buckets:      [AtomicU64; BUCKET_BOUNDS_MICROS.len()],
    duration_micros_total: AtomicU64,
}

pub struct MetricsObserver {
    stats: HashMap<UpstreamId, Arc<UpstreamStats>>,  // fixed at construction
    order: Vec<UpstreamId>,                          // sorted, for a stable scrape
}
```

Three relaxed `fetch_add`s per attempt: one outcome counter, one bucket slot, the microsecond
total. No `count` field and no observer-level totals — both are sums of what is already there, and
deriving them at render keeps the hot path at one write per fact rather than two.

```rust
// src/route/metrics.rs — the view

impl Collector for MetricsCollector {
    fn desc(&self) -> Vec<&Desc> { ... }              // two, built once
    fn collect(&self) -> Vec<MetricFamily> { ... }    // reads the atomics, builds protos
}
```

### What the scorer's read path costs, either way

Under **registry-owns-the-data**, v0.2's clock reading one upstream's success count:
`registry.gather()` → walk `Vec<MetricFamily>` for `rpc_attempts_total` → walk its `Vec<Metric>`
→ match `upstream` and `outcome` against `LabelPair` strings → `get_counter().value()` → `f64`,
cast back to a count. Six steps, two linear scans, string comparison as the lookup key, and a
number that has been through `f64` on the way.

Under **store-owns-the-data**: `observer.stats_for(&id)` → `snapshot()`. Two steps, hash lookup,
`u64` throughout. The clock holds the `Arc<UpstreamStats>` across ticks, so steady state is one
`snapshot()` call per upstream per tick and nothing else.

The exposition still pays the six-step cost — but a scrape is supposed to walk everything and
render it as text, so paying it there is paying it where it belongs.

### The cost, stated honestly

Owning the buckets means owning the exposition. `MetricsCollector` is roughly 120 lines: two
`Desc`s, a `LabelPair` helper, one `Metric` per upstream-and-outcome for the counter family, and
for the histogram a running accumulator that turns per-slot counts into the cumulative `le` form
Prometheus requires. Get the accumulator wrong and `histogram_quantile()` returns garbage with no
error, which is why the invariants are pinned by test rather than by reading.

One thing the crate does give back: supply only the finite bounds and `TextEncoder` derives the
`le="+Inf"` line from `sample_count`. That is what lets an attempt slower than every bound be
counted without a slot to hold it — but it is behaviour taken on trust, so
`the_inf_bucket_is_derived_and_matches_the_count` asserts it rather than assuming it.

## Breaks when

- **The process restarts**: counters reset to zero, and a `rate()` window spanning the restart
  reads it as a negative delta. Prometheus handles counter resets natively; the v0.2 scoring clock
  will not, unless it treats a decrease as "discard this window".
  <!-- TODO: confirm whether that guard belongs here or in v0.2. -->
- **An upstream has served nothing yet**: its counters are all zero, which is indistinguishable
  from "healthy and idle" by ratio alone. Every consumer needs a minimum-sample rule before it
  divides. This is the cold-start problem [draft/v0.2.md](draft/v0.2.md) names, surfacing one
  release earlier than expected.
- **A heavy method runs long**: buckets are fixed at startup and cannot adapt per method, because
  the proxy does not parse the body. A slow `eth_getLogs` and a fast `eth_blockNumber` share one
  histogram, so p99 describes the mix rather than either.
- **`application_host` is widened**: `/metrics` has no auth, so binding `0.0.0.0` publishes the
  proxy's operational state to anything that can reach the port. The metric values carry no keys —
  the label rule above guarantees that — but upstream labels, error rates and traffic volume all
  become readable.
- **Upstreams change at runtime**: they cannot. The map is fixed at construction, so an upstream
  added to `settings.yaml` needs a restart, and a `UpstreamId` not present at startup would have
  nowhere to record.
- **Two upstreams share a label**: their counters merge silently, since `UpstreamId` is the key.
  This is the same collapse issue **#9** describes for routing, now with a second consequence.
- **An upstream is configured but fails to build**: the store is populated from `settings.rpcs`,
  while `build_upstreams` (`src/start_up.rs:78`) drops anything `UpstreamBuilder` rejects and logs
  `upstream_skipped`. The dropped label keeps an all-zero series. Defensible — it *is* configured
  and it *is* serving nothing — but it reads identically to a healthy idle upstream, so it
  compounds the cold-start entry above rather than standing alone.

## Logging

**No new events and no schema change.** The v0.1 schema in [v0.1.md](v0.1.md#logging) stands as
written, and this release adds nothing to it.

`/metrics` deliberately emits no per-request line. Scrapes arrive on a fixed interval forever, and
v0.1 already lists uncapped log volume as an Observability bug — a scraper at 5s would add ~17k
lines a day that say nothing. A failure to render is the exception and is worth a line.

That one line is `event = "metrics_render_failed"` at `error`, carrying the encoder's error and
nothing else. It belongs in the v0.1 lifecycle table rather than a second table here — it is a
failure of a request like any other, and it does not describe a stage of the proxy path.

## Known Bugs

### Closed by this release

- **The observation sink is a no-op** (v0.1.2, New in this release). Every attempt outcome was
  constructed and discarded; it now folds into a per-upstream store.
- **No fleet-level view** (v0.1, Observability). Partially — per-upstream attempt counts, outcome
  classes and latency distributions become queryable. What is still missing is per-method
  breakdown, which needs body parsing.

### Carried forward, still open

Restated rather than referenced, because a version pointer hides which entries are still live.
Full reasoning stays in [v0.1.md](v0.1.md#known-bugs).

**Correctness** — head divergence across upstreams at different chain heights; no retry
classification, so deterministic errors like `execution reverted` are retried across the chain;
JSON-RPC errors riding on HTTP 200 (rate limits as `-32005`) are undetectable under the
status-code-only rule, **and are therefore counted as successes by every metric in this release**;
error responses always carry `id: null`; `eth_sendRawTransaction` retry is unsafe; batch rejection
is a transport-level `[` peek with no JSON-RPC error object.

**Observability** — no JSON-RPC method in logs or metrics; `duration_ms` excludes the inbound body
read; log volume is uncapped at four lines per request; the log schema is still unasserted, because
the writer is not injectable until #7's second half lands.

**Routing and health** — no health state, so a dead upstream is never removed from the rotation.
This release makes that state *measurable* without making it *actionable*; acting on it is v0.2.

**Timeouts and limits** — per-attempt timeout is a fixed value and wrong for heavy methods; no
total deadline; no inbound request timeout; no request body size cap; `Retry-After` response
headers ignored; no exponential backoff.

**Config and naming** — API keys live in YAML; `retry_after` is a misleading name for a flat
inter-attempt delay; a `reqwest::Client` per upstream rather than one shared. `max_attempt` can be
silently unreachable when it exceeds the upstream count.

### New in this release

- **Metrics are attempt-level, not request-level**: a request that fails over twice contributes
  three attempts and no request-scoped record, so "how long did the client wait" is not derivable
  from `/metrics`. The retry loop knows it (`src/proxy.rs:118`); the observer does not.
- **`/metrics` is unauthenticated**: acceptable on loopback, a disclosure the moment
  `application_host` widens. There is no auth middleware to hang it off yet.
- **Histogram buckets are a global guess**: fixed at startup, shared across every method and every
  upstream.
- **Counters do not survive a restart**: no persistence, by design, but it makes every window that
  spans a deploy unreliable rather than merely empty.
