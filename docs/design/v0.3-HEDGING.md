# Ethereum JSON-RPC Proxy (Rust) (v0.3 — HEDGING)

Builds on [v0.2.1-DECIDER.md](v0.2.1-DECIDER.md). The primitives behind every decision here were
drilled first in `tokio-lab/` on `chore/tokio-lab` (ex2, ex4, ex5, ex7, ex9); the card
(`tokio-lab/CARD.md`) is the short form.

## Problem

The proxy walks the decider's chain one upstream at a time. A slow upstream that does not fail
holds the request for its whole latency, up to `rpc_timeout_in_secs`, before anything else is
tried. Failover covers upstreams that break; nothing covers upstreams that are merely slow. The
spec (§4.3) asks for the tail to be cut: past a threshold, race the next-best upstream and take
whichever answers first.

## Goals

- Opt-in hedging, **off by default**. With it off, the request path is exactly today's loop.
- A threshold set globally, overridable per upstream (spec: "configurable per upstream").
- Hedges counted apart from retries — "hedge is patience, retry is failure".
- A write is never sent to more than one upstream by the hedger.

## Not doing

- Adaptive thresholds (p95-derived `hedge_after`). The threshold is a fixed number.
- Hedging batches. Batches are still rejected with 400.
- A hedge budget / rate cap on extra load.
- Recording cancelled losers in the observer (see *Known Bugs*).
- Fixing retries of writes on `Unreachable`, which predate this release.

## Interface

### HTTP
No change. A hedged response is indistinguishable from an unhedged one.

### settings.yaml

```yaml
application:
  proxy:
    hedge:
      enabled: false          # default
      after_in_millis: 250    # default; the global threshold
upstreams:
  - label: alchemy
    url: https://eth-mainnet.g.alchemy.com/v2/${ALCHEMY_KEY}
    hedge_after_in_millis: 400   # optional; overrides the global threshold for this upstream
```

- `after_in_millis` and every override must be at least 1. Zero is a startup error.
- An override at or past `rpc_timeout_in_secs` can never fire. Logged at startup, not rejected.
- `max_attempt` caps total calls per request, hedges included.

## Shape

```
Pipeline::proxy (request task)
  ├─ hedge.enabled == false ─> sequential loop (unchanged, sleeps retry_after)
  └─ hedge.enabled == true  ─> race(chain)
        FuturesUnordered<try_once>   ── polled on this task, no spawn
        select! { biased;
          inflight.next()                       ─ Ok        → return, drop the rest
                                                ─ Err retry → start next now   (retry)
                                                ─ Err final → return it
          sleep(chain[latest].hedge_after), if more ─ start next               (hedge)
        }
        more = next < min(chain.len, max_attempt) && !is_write(body)
```

`hedge_after` is the threshold of the most recently started upstream. The sleep is rebuilt on
every pass of the loop — here that is correct, not the ex3 trap: patience is measured from the
latest start, so a failure that pulls the next upstream in also restarts the clock.

## Sharpest decision

**`FuturesUnordered` on the request's own task, not `JoinSet`.** Hedging lives inside one
`Pipeline::proxy` frame and nothing outlives it. The futures borrow `&self`, the chain and the
body; nothing needs `'static`, `Send` or `Arc<Self>`. `JoinSet` would charge `self: Arc<Self>`
up every caller to buy cross-core parallelism a single proxied request cannot spend (ex7).

**Race for first success, not first completion.** A fast failure does not end the race; it
starts the next upstream at once. If everything fails, the last error is the one the caller
gets, the same as the sequential loop's `last_failure` (ex4).

**A failure is a retry, never a hedge.** Only a call started by the timer increments the hedge
counter. "We got impatient" and "the upstream broke" are two different alerts (ex5).

**A non-retryable error ends the race.** A revert or a malformed request is deterministic —
every upstream answers it the same way. Returning it at once matches the sequential loop's
`break`.

**The write guard is the only double-send protection.** Dropping the loser's future stops our
side; the request is already on the wire and the upstream's handler runs to completion (ex9:
hits = 1 after a drop). So cancellation protects nothing, and `eth_sendRawTransaction`,
`eth_sendTransaction`, `eth_sendRawTransactionConditional`, `eth_sendBundle` and
`eth_sendPrivateTransaction` are never hedged. A body whose method cannot be read counts as a
write. Exactly-once is bought with tail latency; there is no cheaper currency.

**In hedge mode a failure does not wait `retry_after`.** The hedge exists to cut latency; a
backoff sleep after a known failure would hand it straight back.

## Breaks when

- **Every upstream is slow.** Hedging multiplies load by up to `max_attempt` without cutting
  latency. There is no hedge budget.
- **The threshold sits below the healthy median.** Nearly every request hedges, doubling
  upstream spend. The threshold is not derived from observed latency.
- **Upstreams are rate-limited.** Extra calls spend quota and can push a healthy upstream into
  429s, which then read as its errors.
- **A write method is missing from the list.** It gets hedged and may be sent twice.

## Logging

| event | level | fields | when |
|---|---|---|---|
| `attempt_started` | info | `attempt`, `upstream`, `hedge` | every call; `hedge=true` when the timer started it |
| `hedge_started` | info | `attempt`, `upstream`, `after_ms` | the timer fires and starts the next upstream |
| `request_completed` | info | existing, plus `hedges`, `hedge_won` | hedge mode only adds the two fields |

`retries_exhausted` and `attempt_*` are unchanged.

### Metrics

| family | labels | meaning |
|---|---|---|
| `rpc_hedges_total` | `upstream`, `to` | hedge calls started because `upstream` passed its `hedge_after`, sent to `to` |
| `rpc_hedge_wins_total` | `upstream`, `to` | those hedge calls that answered first |

`upstream` is the overtaken (slow) one, `to` the one hedged to. The overtaken call is dropped
and records nothing (see *Known Bugs*), so labelling the hedge with it is the only place its
slowness shows up. `sum by (upstream)` answers "who is slow", `sum by (to)` "who rescues". A
hedge always overtakes the upstream just before it in the chain, since the timer only waits on
the latest start. Every ordered pair is exposed from startup: N upstreams give N×(N−1) series
per family.

Neither feeds the decider's error rate.

## Known Bugs

### New in this release

- **Cancelled losers are invisible.** A dropped call never completes, so the observer records
  nothing: `rpc_attempts_total` undercounts, the latency histogram loses its slowest samples,
  and `PREFER_LEAST_ERRORS` never learns an upstream is slow. The upstream still did the work.
- **The write list is a denylist.** An unknown write method is hedged. An allowlist of
  known-safe reads would fail closed instead.
- **Thresholds are guesses.** 250ms has no traffic behind it.

### Carried forward, still open

Unchanged from v0.2.1. Writes are still retried on `Unreachable`, where the first request may
already have landed.
