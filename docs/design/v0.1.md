# Ethereum JSON-RPC Proxy (Rust) (v0.1)

## Problem

RPC providers exceed their rate limits, endpoints have to be swapped by hand, and every service manages its own
list of RPC URLs.

## Goals

- **Provider outages do not reach users**: if at least one provider is working, the end user should not see an outage.
- **A single request is debuggable from logs**: a dev can take one request, follow it across every upstream attempt,
  and see which upstream failed and why. Fleet-level aggregate observability comes later.

## Not doing

- **Caching**: deferred. Comes once a request can be classified as returning an immutable or a mutable response.
- **Least-latency routing**: plain round robin plus retry failover to another RPC. The latency added by walking the
  chain is acceptable.
- **Auth**
- **Batch handling**: error out for now with HTTP 400
- **Multichain**
- **In-flight dedup**
- **Hedging**
- **Docker image + compose**
- **Metrics**: no Prometheus endpoint and no metrics collection in v0.1. Logs are the only observability surface.

## Interface

### HTTP

| Method | Path | Purpose | Auth |
|---|---|---|---|
| POST | /rpc | Proxy to JSON-RPC | None |
| GET | /healthz | Liveness — is the process up | None |

### settings.yaml

```yaml
application_port: 8080

rpcs:
  - label: alchemy
    rpc_url: https://rpc.alchemy.com/XXXX
  - label: alchemy-1
    rpc_url: https://rpc.alchemy.com/XYXY
  - label: drpc
    rpc_url: https://rpc.drpc.com/XXXX

# Optional, shown with their defaults.
max_attempt: 3
rpc_timeout_in_secs: 3
retry_after_in_secs: 1
```

`application_port` and `rpcs` are required; the rest default. `max_attempt` must be at least 1 — startup fails
otherwise, as it does when no upstream survives construction.

## Shape

```
Req Handler --> Decider{collection of rpcs} --> tokio task fetches RPC, retries on failure
                     ^                                          |
                     |            on failure, ask the Decider again —
                     +----------- it hands back the next rpc in the rotation
                                                                |
                                                                v
                                          respond back through the Req Handler
```

The Decider is a plain round robin over a shared atomic cursor. It takes no arguments and keeps no per-request
state, so it does not know which upstream just failed.

## Sharpest decision

Accepting the tail latency of a serial retry chain.

## Breaks when

- **One RPC fails**: log at `warn`, continue to the next upstream.
- **Every attempt fails**: return a JSON-RPC error envelope — `{"jsonrpc":"2.0","error":{"code":-32603,...},"id":null}`
  — with HTTP 200 and `content-type: application/json`. HTTP 200 is deliberate: clients short-circuit on non-2xx and
  never parse the body, so a 503 would discard the error detail. Covers both upstream-unreachable and
  upstream-read-failure. Note this means the retry budget was spent, not that every configured upstream was
  necessarily tried.
- **Raw JSON-RPC**: requests are forwarded as raw JSON-RPC; error responses still need decoding.
- **Retry bounds**: max attempts, per-attempt timeout, and retry delay are configurable, defaulting to 3 attempts,
  3s, and 1s. Each attempt asks the Decider again and takes whatever the rotation hands back, so attempts are not
  tied to the number of upstreams. No exponential backoff yet.
- **YAML config**
- **RPC failure detection**: a response is treated as failed when the HTTP status is not 200. No error
  deserialisation yet.

## Logging

Logs are the only observability surface in v0.1, so the schema is fixed here rather than left to call sites.

Structured fmt via `tracing` + `tracing-subscriber`, one line per event, written to stdout. `event` is a field, not
the `tracing` message, so a line filters the same way it greps. Colour is emitted only when stdout is a terminal —
redirected output stays free of escape sequences.

`request_id` rides on the request span and so prefixes every line as `proxy{request_id=…}:`; the rest are event
fields.

The body is forwarded raw and never deserialised, so nothing drawn from inside the JSON-RPC payload appears in the
schema — no `method`, no `id`, no params. Every field below comes from the transport layer or from the proxy's own
state. The one exception is a single-byte peek at the first non-whitespace character to reject batches.

**Never log the `rpc` field from `settings.yaml`.** Provider URLs embed the API key in the path, so every log line
refers to an upstream by its `label` only.

### Common fields

Present on every line.

| Field | Type | Notes |
|---|---|---|
| `ts` | RFC3339 string | Event timestamp |
| `level` | string | `info` / `warn` / `error` |
| `event` | string | One of the event names below |
| `request_id` | string | UUID v4, generated per inbound request, ties all lines of one request together |

`request_id` is the one field that can be absent: the lifecycle events below are emitted before the listener
exists, so there is no request to tie them to. Every other line carries all four.

### Lifecycle events

| Event | Level | Extra fields |
|---|---|---|
| `upstream_skipped` | warn | `upstream`, `error` — one entry in `rpcs` failed to construct; the rest still start |
| `startup_ready` | info | `upstreams` (count that survived), `port` — socket is bound and listening |
| `startup_failed` | error | `error` — settings, handler construction, or bind failed; exits 1 |
| `server_stopped` | error | `error` — the accept loop returned; exits 1 |

### Per-request events

| Event | Level | Extra fields |
|---|---|---|
| `request_received` | info | `body_bytes` |
| `batch_rejected` | warn | `body_bytes` — first non-whitespace byte was `[`, answered with HTTP 400 |
| `attempt_started` | info | `attempt`, `upstream` (label) |
| `attempt_failed` | warn | `attempt`, `upstream`, `duration_ms`, `http_status`, `error` |
| `attempt_succeeded` | info | `attempt`, `upstream`, `duration_ms`, `http_status`, `response_bytes` |
| `request_completed` | info | `attempts`, `upstream`, `duration_ms` |
| `retries_exhausted` | error | `attempts`, `tried` (labels in attempt order, may repeat), `duration_ms`, `error` (last failure) |

`attempt` is 1-indexed. On `request_completed`, `attempts` is the total number made and `upstream` is the label of
the one that answered. `duration_ms` on `request_completed` and `retries_exhausted` is measured inbound to
outbound; on the `attempt_*` events it covers that attempt alone.

`http_status` is absent on `attempt_failed` when the transport failed before a response arrived — there is no
status to report. It is present when the read failed mid-body and when the status itself was the failure.

`error` on `retries_exhausted` is the full text of the last failure, not a category: it carries the upstream's
own message and the failing status code, so the tail of a request is legible without also grepping the
`attempt_failed` lines.

Correlating a failure means grepping one `request_id` and reading the `attempt_*` lines in order — that sequence is
what makes an outage legible without metrics.

## Known Bugs

Everything below is known-broken or knowingly absent in v0.1 and gets picked up in a later iteration.

### Correctness

- **Head-divergence hazard**: multiple upstreams sit at different chain heights. `eth_blockNumber` → A says 100;
  the next call `eth_getBlockByNumber(100)` → B says null. Round robin makes this frequent. This is the #1
  real-world bug of multi-upstream proxies.
- **Retry classification**: the system is blind to which errors are retryable. `execution reverted` is
  deterministic — every upstream returns the same answer, so retrying it is pure latency. Rate limits, transport
  errors, and 5xx should be retried; deterministic execution errors should not. Added once responses can be
  classified.
- **Error detection failure**: some JSON-RPC errors ride on HTTP 200 — rate limits arrive as 200 with `-32005`.
  These are not detectable under the current status-code-only rule.
- **Error responses always carry `id: null`**: the JSON-RPC envelope is now returned (see "Every attempt fails"),
  but the caller's `id` is not echoed, because raw passthrough never parses the request body. Spec-conformant
  clients match responses to requests by `id`; a `null` breaks that correlation, and a client with several requests
  in flight cannot tell which one failed. Cost to fix is one partial parse of the already-buffered body to pull
  `id` — roughly ten lines, and independent of retry classification. Deferred by choice, not blocked.
- **`eth_sendRawTransaction` retry is unsafe**: a retry lands on a second upstream that answers "already known",
  which the current detector reads as a failure and escalates. Falls out of retry classification.
- **Batch rejection is transport-level only**: batches are detected by peeking for a leading `[` and answered with
  HTTP 400. A caller gets no JSON-RPC error object, and a malformed non-batch body is not distinguished from a
  batch — both just fail somewhere downstream.
- **Retries can land on the upstream that just failed**: the Decider takes no exclusion, so a retry gets the next
  entry in the rotation regardless of what failed. With one upstream configured, every retry hits it. With
  concurrent traffic advancing the shared cursor, an attempt can wrap onto the same upstream before the rotation
  completes. Retry breadth is therefore best-effort, not a guarantee that N attempts touch N distinct providers.

### Observability

- **No fleet-level view**: logs answer "what happened to this request", not "which upstream is degrading" or "what
  is the p95". Aggregate observability needs either metrics or a log aggregator (Loki, ES), and v0.1 ships neither
  and names neither as a dependency. Comes with the metrics work.
- **No JSON-RPC method in logs**: raw passthrough means the body is never parsed, so no log line says which method
  failed. A dev can see that upstream `drpc` returned 500 on attempt 2, but not that it was an `eth_getLogs`. This
  is the main cost of the passthrough decision and it lands squarely on the debuggability goal. Cost to fix is the
  same partial parse as the `id` item above — pull `method` from the already-buffered body and add it to the common
  fields. Not gated on retry classification. Deferred by choice, not blocked.
- **`duration_ms` is not quite inbound to outbound**: the timer starts after axum's `Bytes` extractor has
  buffered the whole request body, so the inbound read is excluded. Negligible at current body sizes; it becomes
  a real gap once "no request body size cap" below is fixed and large POSTs are in play.
- **Log volume is uncapped**: the happy path emits four lines per request (`request_received`, `attempt_started`,
  `attempt_succeeded`, `request_completed`). A proxy in front of every RPC call an app makes will produce a lot of
  stdout. No sampling, no per-event level control, no way to drop the `attempt_*` pair at info.

### Routing and health

- **No health state**: a dead upstream is never removed from the rotation, so 1/N of requests keep paying the full
  retry chain. Spec 4.2 ("failing upstream removed from the pool, re-admitted on recovery") is not met.

### Timeouts and limits

- **Per-attempt timeout is fixed**: 3s is wrong for heavy methods. `eth_getLogs` over a wide range,
  `debug_traceTransaction`, and fat `eth_call`s legitimately run longer, so they time out and then get retried
  across every upstream — one slow-but-succeeding request becomes several failed ones. Per-method-class timeouts
  come with request classification.
- **No total deadline**: worst case is roughly `max_attempt * rpc_timeout + (max_attempt - 1) * retry_after` ≈ 11s
  with the defaults, and nothing caps it.
- **No inbound request timeout**
- **No request body size cap**: a large POST is read into memory unbounded.
- **`Retry-After` response headers are ignored**: a 429 is retried immediately against the next upstream instead of
  respecting the upstream's backoff.
- **No exponential backoff**: `retry_after` is a flat delay.

### Config and naming

- **API keys live in YAML**: `settings.yaml` is gitignored, which covers accidental commits. It does not cover
  image layers, mounted config volumes, or backups. The spec constraint is env-var injection; v0.1 does not do it.
- **The listener address is hardcoded to `127.0.0.1`**: only the port is configurable, so the proxy is unreachable
  from outside the host it runs on.
- **`retry_after` is a misleading name**: HTTP `Retry-After` is a response header sent by the upstream, and this
  field is a flat inter-attempt delay. Rename to `retry_delay` when the config is next touched.
- **A `reqwest::Client` per upstream, not one shared**: each `RpcHandler` builds its own client, so each keeps its
  own connection pool. Keepalive per upstream still works, but the pools are not shared and the client count scales
  with the upstream count. The shape falls out of the per-attempt timeout being set on the client rather than
  per-request; sharing one client means moving the timeout to the request builder.

### Process

- **No done criteria**: v0.1 has no written definition of finished. A controllable fake upstream now exists
  (`wiremock`, in `tests/common/mock_rpc_server.rs`) and covers passthrough, even rotation, failover past a dead
  upstream, and retry exhaustion. Still uncovered: batch rejection, the per-attempt timeout firing, and the log
  schema — tests never call `telemetry::init`, so no assertion touches a log line.
