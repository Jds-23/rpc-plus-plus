# Ethereum JSON-RPC Proxy (Rust) (v0.4 — DEDUP)

Builds on [v0.3-HEDGING.md](v0.3-HEDGING.md). Caching belongs to a later release.

## Problem

Every request reaches an upstream on its own. Ten wallets polling `eth_blockNumber` in the same
100ms make ten upstream calls for one answer, and pay ten times the quota for it. The spec (§3.4)
asks for concurrent identical requests — same method, same params — to be coalesced into one
upstream call, with every waiting caller receiving that call's response.

## Goals

- Opt-in dedup, **off by default**. With it off, the request path is exactly today's.
- Coalesce concurrent identical **reads** only. A write is never coalesced.
- Every caller gets its own `id` back, and the result byte for byte.
- A caller hanging up never fails the callers still waiting.
- Dedup is not a cache: a request arriving after a flight finished makes a fresh call.

## Not doing

- Caching of any kind, finalized or otherwise (spec §3.3; next release).
- Coalescing batches. Batches are still rejected with 400.
- Coalescing notifications (requests without an `id`).
- Normalising params beyond JSON parsing: `"0xA"` and `"0xa"` are two keys.
- Coalescing across proxy instances.

## Interface

### HTTP
No change. A coalesced response is indistinguishable from an uncoalesced one, `id` included.

### settings.yaml

```yaml
application:
  proxy:
    dedup:
      enabled: false   # default
```

Hedging and dedup compose: a flight runs whichever `Dispatch` path (`walk`, `race` or
`send_once`) the request would have run alone.

## Shape

```
Pipeline::proxy (request task)
  └─ Shape::Single
       ├─ dedup off, or no key, or no id ─> start: decide + run (unchanged path)
       └─ key = jsonrpc::dedup_key(body), id = jsonrpc::request_id(body)
            SingleFlight::join(key, me, make)  ── std Mutex, held for the lookup only
              ├─ live entry (WeakShared::upgrade) → clone the Flight     (follower)
              └─ none / dead                      → new Flight + Evict   (leader)
            reply = flight.await                  ── Shared<Run<Reply>>, Run = BoxFuture<'static, _>
            follower: jsonrpc::readdress(reply.body, id)
              ├─ Some(bytes) → respond
              └─ None        → run this request on its own
```

`Reply { http_status, body: Bytes }` is what a flight shares: an axum `Response` is not `Clone`,
its body reads once. `Bytes::clone` is a refcount bump — fifty followers of a 2MB `eth_getLogs`
share one allocation.

The map holds `Entry { id, leader, flight: WeakShared<_> }`, never a `Shared`: the map alone must
not keep a run alive. An `Evict` guard lives inside the flight's future and removes the entry on
drop — on success, on error, and when every caller hung up mid-flight. It removes only if the
entry is still *its* flight (`id`), so a late drop never evicts the flight that replaced it.

A flight is `'static`, so it cannot borrow the `Pipeline`. The state a run needs lives in
`Core` behind `Pipeline { core: Arc<Core>, flights }`; `run(core, chain, body, received_at)`
owns everything it touches.

## Sharpest decision

**`Shared` on the request's task, not a spawned flight.** Every caller polls the same `Shared`;
whoever is still polling drives the run. The leader hanging up costs nothing — there is no
leader to lose. When *every* caller hangs up, the last `Shared` drop takes the run with it: no
upstream call paid for and answered to no one. A spawned flight survives that, which only earns
its keep once a cache exists to put the orphaned answer in — the next release's question, not
this one's. Same reasoning as v0.3's `FuturesUnordered` over `JoinSet`: nothing outlives the
requests that want it.

**The broadcast-channel design is out.** A leader that runs the call and broadcasts the answer
strands every follower the moment its own client disconnects — and axum drops the handler
future on disconnect, so on a busy proxy that is routine.

**The key is `method` + `params`, parsed.** `id` and `jsonrpc` are the caller's envelope, not the
question. Built from the parsed `Value`, so whitespace and object key order never split a key; a
missing `params` asks the same question as `[]`. `serde_json::Map` is a `BTreeMap` without
`preserve_order`, so serialization writes keys sorted for free — a test guards against the
feature arriving through unification.

**Coalescable = `is_idempotent_read`.** The same allowlist hedging uses, same reasoning: an
unknown method fails closed and only loses a dedup. Two identical sends are two intents;
coalescing one away is a lost write.

**Re-address through `RawValue`, never `Value`.** The leader's body carries the leader's `id`. A
`BTreeMap<&str, &RawValue>` swaps `id` and passes `result` / `error` through untouched — no key
reordering, no `2.50` → `2.5`, no full parse of a 2MB result per follower.

**Dedup sits outside the retry loop.** A flight is a whole request — chain, retries, hedges — not
one call. A failure is shared as-is and never remembered; the next caller retries.

**Only the leader decides.** The chain is picked inside the leader's `make`, so a follower never
advances the decider.

## Breaks when

- **The leader's answer is wrong for a follower.** Two callers that asked the same question get
  the same answer — by design. A caller depending on landing on a specific upstream loses that.
- **One request is slow.** Every follower waits as long as the leader's flight, hedges included.
- **Keys explode.** Every distinct read is one map entry for its flight's lifetime. Bounded by
  concurrent requests, not by history — but unbounded.
- **`serde_json/preserve_order` gets enabled.** Object key order splits keys; dedup silently
  stops coalescing. The key-order test fails first.
- **Two questions hash alike.** The key is a 128-bit xxh3, not the params themselves; a
  collision merges two questions and serves one caller the other's answer. Negligible, not
  zero, and not adversary-proof.

## Phases

One PR per phase, stacked. Every phase ends green on
`cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`.

### P1 — the dedup key (#32)
- `src/jsonrpc.rs`: `pub(crate) struct DedupKey(u128)` and
  `pub(crate) fn dedup_key(body) -> Option<DedupKey>`. Parse a `Value::Object`; method must pass
  `is_idempotent_read`; `params` missing → `[]`; key is the xxh3-128 of the serialized method and
  params, written straight into the hasher (no allocation).
- `None` for writes, unknown methods, batches, malformed bodies.
- `✨ feat: derive dedup key from method and params`

### P2 — a shareable reply (#32, no behaviour change)
- `try_once` returns `Reply { http_status, body: Bytes }`, `Clone` — the same pair
  `CallOutcome { http_status, response_body }` carries.
- `Answered { reply, upstream }`; `finish()` returns `Reply`.
- `jsonrpc::rpc_error` becomes `rpc_error_body -> Bytes`; `Reply::rpc_error` wraps it.
- `impl IntoResponse for Reply`, applied once in `proxy_inner`'s `Single` arm — a 400 for a
  batch or malformed body stays bare.
- `🧹 refactor(proxy): carry reply as status and bytes`

### P3 — re-address the reply (#32)
- `serde_json` gains the `raw_value` feature.
- `jsonrpc.rs`: `pub(crate) fn request_id(body) -> Option<Box<RawValue>>` (`None` for a
  notification; `null` is an id) and `pub(crate) fn readdress(body, id) -> Option<Bytes>`.
- `✨ feat(proxy): re-address a shared reply to the caller's id`

### P4 — singleflight (#33)
- Private `src/proxy/singleflight/`, items `pub(super)`:
  - `mod.rs`: `SingleFlight<T>`, `Run<T>`, `Flight<T>`, `Role { Leader, Follower { leader } }`,
    `join(key, me, make) -> (Flight<T>, Role)`. std `Mutex`, never held across `.await`.
  - `evict.rs`: `Entry { id, leader, flight }`, the id-checked `Evict` drop guard, `lock`.
  - `test.rs`: one leader per key, follower learns the leader; 20 callers → 1 run; finished
    flight leaves the map; not a cache; failure not remembered; leader aborted → followers OK;
    everyone aborted → entry gone and the run dropped; a stale `Evict` spares its replacement.
- `Pipeline { core: Arc<Core> }`; `walk` / `send_once` / `race` on `Core`; free `run` is
  `Send + 'static` (compile-only test).
- `✨ feat(proxy): add singleflight with weak-entry cleanup`

### P5 — wire it in (#34)
- `src/config.rs`: `DedupSettings { enabled }`, default `false`, mirroring `HedgeSettings`.
  `Pipeline::builder().dedup(..)` from `src/app.rs`.
- `Pipeline::start` decides the chain and returns the run; `Pipeline::coalesce` joins, awaits,
  re-addresses, falls back to `start` on `None`.
- Integration tests in `tests/rpc_proxy.rs` (wiremock with a delay): N concurrent identical
  reads → 1 upstream hit, each caller its own id; two identical `eth_sendRawTransaction` → 2 hits;
  different params → 2 hits; leader client dropped mid-flight → followers answered; not a
  cache; dedup off → N hits.
- `✨ feat(proxy): coalesce concurrent identical reads`

### P6 — metric
- `Observer::record_coalesced(&self)`; `MetricsObserver` counts it in an atomic; `Collector`
  renders `rpc_requests_coalesced_total`. `proxy` knows nothing about prometheus: no counter on
  the builder, no registration in `app.rs`.
- `🪵 feat(observer): count coalesced requests`

## Logging

| event | level | fields | when |
|---|---|---|---|
| `request_coalesced` | info | `leader_request_id` | a request joined a flight already in the air |
| `readdress_failed` | warn | `leader_request_id` | the shared reply could not take the follower's id; it runs alone |

`request_completed`, `retries_exhausted` and `attempt_*` are unchanged; they fire once per flight,
under the leader's span. A follower's own span carries only `request_received` and
`request_coalesced`. Rust API says *call*, logs say *attempt* — unchanged here.

### Metrics

| family | labels | meaning |
|---|---|---|
| `rpc_requests_coalesced_total` | — | requests answered by another request's flight |

Not fed to the decider: a coalesced request made no call. Counted once the follower's reply is
re-addressed; a `readdress_failed` fallback made its own call and is not counted. Always rendered
by `Collector`, so it reads `0` with dedup off rather than going missing.

## Known Bugs

### New in this release

- **Followers inherit the leader's span.** Their `attempt_*` lines carry the leader's
  `request_id`; joining them back goes through `request_coalesced.leader_request_id`.
- **Hex case splits keys.** `"0xA"` and `"0xa"` are the same block and two flights.
- **`rpc_error` replies are re-addressed too.** Today they carry `"id": null`; with dedup on, a
  follower's copy carries its own id while the leader's — and every uncoalesced one — keeps `null`.
- **A follower's latency is logged nowhere.** `request_completed` is the leader's, with the
  leader's `duration_ms`; a follower that joined late waited less, one that fell back waited more.
- **The fallback costs a second wait.** A follower whose reply cannot be re-addressed (a
  non-object upstream body, an escaped `"id"` key) runs alone only after the whole flight —
  up to twice the latency.
- **Load spread tracks flights, not requests.** Only the leader asks the decider for a chain, so
  round-robin advances once per flight; a hot key lands on whichever upstream its leader drew.
- **Each body is parsed about four times** (`shape`, `dedup_key`, `request_id`, `is_write`). A
  single parse into one request view belongs under #20 / #23.
