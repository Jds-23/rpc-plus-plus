# Ethereum JSON-RPC Proxy (Rust) (v0.4 — DEDUP)

Builds on [v0.3-HEDGING.md](v0.3-HEDGING.md). The primitives behind every decision here were
drilled first in `dedup-lab/` on `feat/dedup-lab` (ex1–ex5); the card (`dedup-lab/CARD.md`) is
the short form. The cache drills (ex6–ex8) belong to a later release.

## Problem

Every request reaches an upstream on its own. Ten wallets polling `eth_blockNumber` in the same
100ms make ten upstream calls for one answer, and pay ten times the quota for it. The spec (§3.4)
asks for concurrent identical requests — same method, same params — to be coalesced into one
upstream call, with every waiting caller receiving that call's response.

## Goals

- Opt-in dedup, **off by default**. With it off, the request path is exactly today's.
- Coalesce concurrent identical **reads** only. A write is never coalesced.
- Every caller gets its own `id` back, and the result byte for byte.
- A caller hanging up never fails the callers still waiting.
- Dedup is not a cache: a request arriving after a flight finished makes a fresh call.

## Not doing

- Caching of any kind, finalized or otherwise (spec §3.3; ex6–ex8, next release).
- Coalescing batches. Batches are still rejected with 400.
- Coalescing notifications (requests without an `id`).
- Normalising params beyond JSON parsing: `"0xA"` and `"0xa"` are two keys.
- Coalescing across proxy instances.

## Interface

### HTTP
No change. A coalesced response is indistinguishable from an uncoalesced one, `id` included.

### settings.yaml

```yaml
application:
  proxy:
    dedup:
      enabled: false   # default
```

Hedging and dedup compose: a flight runs whichever path (`walk` or `race`) the request would
have run alone.

## Shape

```
Pipeline::proxy (request task)
  └─ Shape::Single
       ├─ dedup off, or no key, or no id ─> walk / race (unchanged)
       └─ key = dedup_key(body), id = request_id(body)
            SingleFlight::join(key)            ── std Mutex, held for the lookup only
              ├─ live entry (WeakShared::upgrade) → clone the Flight     (follower)
              └─ none / dead                      → new Flight + Evict   (leader)
            reply = flight.await                  ── Shared<BoxFuture<'static, Reply>>
            readdress(reply.body, id)
              ├─ Some(bytes) → respond
              └─ None        → run this request on its own
```

`Reply { status, body: Bytes }` is what a flight shares: an axum `Response` is not `Clone`, its
body reads once. `Bytes::clone` is a refcount bump — fifty followers of a 2MB `eth_getLogs` share
one allocation (ex5).

The map holds a `WeakShared`, never a `Shared`: the map alone must not keep a call alive. An
`Evict` guard lives inside the flight's future and removes the entry on drop — on success, on
error, and when every caller hung up mid-flight. It removes only if the entry is still *its*
flight (`u64` id), so a late drop never evicts the flight that replaced it (ex4).

## Sharpest decision

**`Shared` on the request's task, not a spawned flight.** Every caller polls the same `Shared`;
whoever is still polling drives the call. The leader hanging up costs nothing — there is no
leader to lose (ex3). When *every* caller hangs up, the last `Shared` drop takes the call with
it: no upstream call paid for and answered to no one. A spawned flight survives that, which only
earns its keep once a cache exists to put the orphaned answer in — the next release's question,
not this one's. Same reasoning as v0.3's `FuturesUnordered` over `JoinSet`: nothing outlives the
requests that want it.

**The broadcast-channel design is out.** A leader that runs the call and broadcasts the answer
strands every follower the moment its own client disconnects — and axum drops the handler
future on disconnect, so on a busy proxy that is routine (ex3).

**The key is `method` + `params`, parsed.** `id` and `jsonrpc` are the caller's envelope, not the
question. Built from the parsed `Value`, so whitespace and object key order never split a key; a
missing `params` asks the same question as `[]` (ex1). `serde_json::Map` is a `BTreeMap` without
`preserve_order`, so `Display` writes keys sorted for free — a test guards against the feature
arriving through unification.

**Coalescable = `is_hedge_safe`.** Same allowlist, same reasoning: an unknown method fails closed
and only loses a dedup. Two identical sends are two intents; coalescing one away is a lost write.

**Re-address through `RawValue`, never `Value`.** The leader's body carries the leader's `id`. A
`BTreeMap<&str, &RawValue>` swaps `id` and passes `result` / `error` through untouched — no key
reordering, no `2.50` → `2.5`, no full parse of a 2MB result per follower (ex5).

**Dedup sits outside the retry loop.** A flight is a whole request — chain, retries, hedges — not
one call. A failure is shared as-is and never remembered; the next caller retries (ex4).

## Breaks when

- **The leader's answer is wrong for a follower.** Two callers that asked the same question get
  the same answer — by design. A caller depending on landing on a specific upstream loses that.
- **One request is slow.** Every follower waits as long as the leader's flight, hedges included.
- **Keys explode.** Every distinct read is one map entry for its flight's lifetime. Bounded by
  concurrent requests, not by history — but unbounded.
- **`serde_json/preserve_order` gets enabled.** Object key order splits keys; dedup silently
  stops coalescing. The key-order test fails first.
- **Two questions hash alike.** The key is a 128-bit xxh3, not the params themselves; a
  collision merges two questions and serves one caller the other's answer. Negligible, not
  zero, and not adversary-proof.

## Phases

One branch, one commit per phase. Every phase ends green on
`cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`.

### P1 — the dedup key (ex1)
- `src/proxy/dedup_key.rs`: `DedupKey(u128)` and `dedup_key(body) -> Option<DedupKey>`. Parse
  a `Value::Object`; method must pass `is_hedge_safe`; `params` missing → `[]`; key is the
  xxh3-128 of the serialized method and params, written straight into the hasher (no
  allocation). Array order kept, object keys sorted.
- `None` for writes, unknown methods, batches, malformed bodies.
- Port ex1's tests as unit tests.
- `✨ feat(proxy): derive dedup key from method and params`

### P2 — a shareable reply (no behaviour change)
- `try_once` (`src/proxy/attempt.rs`) returns `Reply { status, body: Bytes }`, `Clone`.
- `Finished` carries `Reply`; `finish()` returns `Reply`. `hedge::race` is already generic over
  its output.
- Split `rpc_error` into a body builder and the `Response` wrapper.
- `impl IntoResponse for Reply`, applied once in `proxy_inner`'s `Single` arm — a 400 for a
  batch or malformed body stays bare, with no JSON content type.
- Existing `tests/rpc_proxy.rs` stays green untouched.
- `🧹 refactor(proxy): carry reply as status and bytes`

### P3 — re-address the reply (ex5)
- `serde_json` gains the `raw_value` feature.
- `jsonrpc.rs`: `request_id(body) -> Option<Box<RawValue>>` (`None` for a notification) and
  `readdress(body, id) -> Option<Bytes>` via `BTreeMap<&str, &RawValue>`.
- Port ex5's tests: own id per caller, result byte for byte, `null` stays `null`, errors
  re-addressed, non-object → `None`.
- `✨ feat(proxy): re-address a shared reply to the caller's id`

### P4 — singleflight (ex2 + ex4)
- `src/proxy/singleflight.rs`: `Arc<Mutex<HashMap<DedupKey, (u64, WeakShared<Call>)>>>`,
  `AtomicU64` flight ids, id-checked `Evict` drop guard inside the flight future.
  `join(key, make) -> (Flight, Role)`. std `Mutex`, never held across `.await`. (P5 adds the
  leader's request id: `join(key, leader, make)`, `Role::Follower { leader }`.)
- The flight is `'static`: move `Pipeline`'s state behind `Arc<Inner>` so the future owns it,
  the chain and the body.
- Port ex2/ex4/ex3 tests on a paused clock: 20 callers → 1 call; finished flight leaves the map;
  a later caller makes a fresh call; a failure is not remembered; leader aborted → followers OK;
  everyone aborted → entry gone and the call dropped.
- `✨ feat(proxy): add singleflight with weak-entry cleanup`

### P5 — wire it in
- `src/config.rs`: `application.proxy.dedup.enabled`, default `false`, mirroring `hedge`.
  `Pipeline::builder().dedup(..)` from `src/app.rs`.
- `proxy_inner`: dedup on + key + id → join, await, re-address; re-address `None` → run alone.
- Follower logs `request_coalesced`; the flight runs under the leader's span.
- Integration tests in `tests/rpc_proxy.rs` (wiremock with a delay): N concurrent identical
  reads → 1 upstream hit, each caller its own id; two identical `eth_sendRawTransaction` → 2 hits;
  different params → 2 hits; leader client dropped mid-flight → followers answered; dedup off →
  N hits.
- `✨ feat(proxy): coalesce concurrent identical reads`

### P6 — metric and docs
- `rpc_requests_coalesced_total`, pipeline-level (not per upstream), registered in `app.rs`.
- Fill this doc's *Logging* and *Known Bugs* from what P1–P5 actually shipped.
- `🪵 feat(observer): count coalesced requests`

## Logging

| event | level | fields | when |
|---|---|---|---|
| `request_coalesced` | info | `leader_request_id` | a request joined a flight already in the air |
| `readdress_failed` | warn | `leader_request_id` | the shared reply could not take the follower's id; it runs alone |

`request_completed`, `retries_exhausted` and `attempt_*` are unchanged; they fire once per flight,
under the leader's span. A follower's own span carries only `request_received` and
`request_coalesced`. Rust API says *call*, logs say *attempt* — unchanged here.

### Metrics

| family | labels | meaning |
|---|---|---|
| `rpc_requests_coalesced_total` | — | requests answered by another request's flight |

Not fed to the decider: a coalesced request made no call. Counted once the follower's reply is
re-addressed; a `readdress_failed` fallback made its own call and is not counted. Registered
even with dedup off, so it reads `0` rather than going missing.

## Known Bugs

### New in this release

- **Followers inherit the leader's span.** Their `attempt_*` lines carry the leader's
  `request_id`; joining them back goes through `request_coalesced.leader_request_id`.
- **Hex case splits keys.** `"0xA"` and `"0xa"` are the same block and two flights.
- **`rpc_error` replies are re-addressed too.** Today they carry `"id": null`; with dedup on, a
  follower's copy carries its own id while the leader's — and every uncoalesced one — keeps `null`.
- **A follower's latency is logged nowhere.** `request_completed` is the leader's, with the
  leader's `duration_ms`; a follower that joined late waited less, one that fell back waited more.
- **The fallback costs a second wait.** A follower whose reply cannot be re-addressed (a
  non-object upstream body, an escaped `"id"` key) runs alone only after the whole flight —
  up to twice the latency.
- **Load spread tracks flights, not requests.** Only the leader asks the decider for a chain, so
  round-robin advances once per flight; a hot key lands on whichever upstream its leader drew.

Unchanged from v0.3.
