# Ethereum JSON-RPC Proxy (Rust) (v0.1.2)

## Problem

v0.2 wants health-scored routing: a background clock that snapshots per-upstream metrics, scores
every upstream, and publishes an ordered plan the request path reads. The v0.1 code cannot host that
design, and the reasons are structural rather than stylistic.

Paths in this section name the v0.1 code this release was written against. Where an item has since
landed, the current location follows in parentheses.

- **The Decider hands back a borrow.** `decide()` returns `Option<&Self::Item>` tied to `&self`.
  A plan published through an `ArcSwap` is read behind a guard; a reference into it cannot outlive
  the guard, and the request path holds the chosen upstream across an `await`. Every v0.2 shape dies
  on this signature. (Landed in #3 — `src/decider.rs:10` returns `Vec<Arc<RpcHandler>>`.)
- **The state type is named after the algorithm v0.2 deletes.** `RoundRobinHandler`, `Inner`, and
  `src/rpc_handler/round_robin_handler.rs` hardcode `RoundRobin<RpcHandler>` as a field
  (`round_robin_handler.rs:95`). Swapping the routing strategy means editing the request path, the
  builder, the router, and every test helper in the same change. (Landed — `ProxyState` in
  `src/proxy.rs:19`, holding an `Arc<dyn Decider>`.)
- **There is no composition root.** `main.rs` loads settings, builds handlers, binds, and serves
  inline (`src/main.rs:10-47`), and the integration tests bypass it entirely by constructing an
  `Arc<Inner>` by hand. v0.2's background loop has nowhere to be spawned and nothing that could test
  it. (Partly landed in #2 — bind and serve moved to `start_up::start`, `src/start_up.rs:44`. Tests
  still build the state by hand and call `build_router` directly, `tests/common/mod.rs:16`; closing
  that is #5.)

v0.1.2 is a bridge release. It reshapes the code so that v0.2 is "add a scoring loop and a second
`Decider` impl" rather than surgery on the request path. One routing behavior changes, deliberately
and visibly; nothing else does.

Tracked as #3 (chain), #4 (attempt outcomes), #5 (composition root), landing after #2. #2 goes first
because #4 widens an error message into a JSON envelope that #2 moves off string interpolation; #3 is
independent but touches the same retry loop, so it goes second to avoid a merge conflict rather than
for any logical dependency.

**Status.** #2 and #3 have landed. #4 and #5 are open; #4 is now unblocked, and it also owns creating
the `UpstreamId` key below, which #3 did not deliver — the chain hands back `Arc<RpcHandler>` and
identity is still `RpcHandler::label() -> &str`.

## Goals

- **v0.2's decider drops in without touching the request path**: adding a new routing strategy means
  writing one `Decider` impl and changing one line at the construction site.
- **A per-attempt result is recordable**: the outcome of every upstream attempt — class, latency,
  status — exists as a value that something other than a log line can consume.
- **Startup and shutdown are one code path, and tests use it**: the same function that `main` calls
  is the one integration tests boot, so anything spawned at startup is testable.

## Not doing

Carried forward from v0.1: caching, least-latency routing, auth, batch handling (still HTTP 400),
multichain, in-flight dedup, hedging.

New to this release, and deferred on purpose:

- **Health scoring, exclusion lists, metrics storage**: the seams land here, the logic lands in v0.2.
  The observation sink is a no-op impl.
- **`/metrics` endpoint and Prometheus registry**: no new HTTP surface.
- **Injectable log writer**: `telemetry::init` keeps writing to stdout, so the log schema still has
  no test asserting it.
- **Env-var config and configurable bind host**: the listener stays on `127.0.0.1` and API keys stay
  in `settings.yaml`.
- **Body parsing**: raw passthrough holds. No `method`, no `id`, no `finality` — which is also why
  the observation sink is keyed by upstream alone rather than v0.2's `(upstream, method, finality)`.

Two of these are **v0.2's entry blockers**, not open-ended deferrals, and are tracked as issues so
the deferral does not go quiet:

- **#6** — env-var secrets and a configurable bind address. Hard prerequisites for v0.2's Docker
  goal; a container binding loopback is unreachable, and keys in YAML violate `docs/spec.md:103`.
- **#7** — `/metrics` route and an injectable log writer. Prerequisites for v0.2's observability
  goal, and the issue corrects v0.2's interface table: export counters, not precomputed error-rate
  gauges.

Both are excluded from v0.1.2 to keep this release free of new external surface, and both must land
before v0.2 starts.

## Interface

Unchanged. `POST /rpc`, `GET /healthz`, and the same `settings.yaml` with the same five keys and the
same defaults. A release with no interface delta is the point: every change here is internal shape,
so the only externally visible difference is the attempt-count behavior described under *Sharpest
decision*.

## Shape

```
 Req Handler
      │
      │ 1. decide()  (once per request, not once per attempt)
      v
 Arc<dyn Decider> ─────> chain: [rpc_b, rpc_c, rpc_a]
      │                        distinct upstreams,
      │                        len = min(max_attempt, upstream_count)
      │
      │ 2. walk the chain, advance on failure
      v
 +------------------------------+           +---------------------------+
 | try_once -> AttemptOutcome   |  keyed by | Observation sink (no-op)  |
 | { class, duration,           | ────────> |                           |
 |   http_status, error }       | UpstreamId| v0.2: metrics db          |
 +------------------------------+           +---------------------------+
      │
      v
 respond via Req Handler
```

`UpstreamId` is not a type yet — #3 landed the chain as `Vec<Arc<RpcHandler>>` and left identity as
`RpcHandler::label() -> &str`, so #4 creates the key along with the outcome.

Two attachment points are what this release exists to create. v0.2 replaces `Arc<dyn Decider>` with
an impl that reads an `ArcSwap<Plan>` — possible only once `decide()` returns owned handles — and
implements the observation sink as the metrics db the background loop snapshots. Neither change
touches the retry loop.

## Sharpest decision

**`max_attempt` becomes a cap over distinct upstreams rather than a retry budget.**

In v0.1 the loop asks the Decider once per attempt (`round_robin_handler.rs:134-146`), so attempts
are not tied to the number of upstreams: the rotation can hand back the same upstream twice, and with
one upstream configured every attempt hits it. Under a chain, the length is
`min(max_attempt, upstream_count)` and every entry is distinct. Landed in #3 — the chain is now
decided once and walked at `src/proxy.rs:92-129`.

Worked example — one upstream configured, `max_attempt: 3`:

```
v0.1:    attempt 1 -> a (fail), sleep, attempt 2 -> a (fail), sleep, attempt 3 -> a (fail)
v0.1.2:  attempt 1 -> a (fail)
```

Three network calls and two `retry_after` sleeps become one call and no sleep. For a genuinely dead
upstream that is strictly better; for a flapping one it removes a retry that sometimes succeeded.
The trade is accepted because retrying the upstream that just failed was already listed as a v0.1
bug, and because v0.2's health scoring needs attempt counts to mean "distinct upstreams tried" for
its error rates to be interpretable.

This is the one behavior change in the release. It is called out here rather than buried in a
refactor because integration tests encoded the old counts: the fallback upstream was expected to
receive 3 calls across 4 requests. `tests/rpc_proxy.rs:115` now asserts 2, with the reason in the
comment above it.

## Breaks when

- **One upstream configured**: the chain has one entry, so a failure is answered after a single
  attempt with no retry delay. `max_attempt` is silently not reached. This is the case most likely
  to surprise someone reading only `settings.yaml`.
- **`max_attempt` exceeds the upstream count**: the chain truncates to the upstream count. The
  configured value is a ceiling that may never be hit; nothing warns at startup.
- **Every chain entry fails**: unchanged from v0.1 — a JSON-RPC error envelope, code `-32603`, HTTP
  200, `id: null`. `retries_exhausted.error` now carries the full text of the last failure rather
  than a category, per issue #2.
- **Zero upstreams**: still rejected at build time (`RoundRobinBuildError::EmptyHandlers`,
  `src/decider/round_robin.rs:36`). The defensive `decide()` → `None` branch in the retry loop
  collapsed into an empty-chain check (`src/proxy.rs:101`).
- **Concurrent traffic**: the cursor advances once per request rather than once per attempt, so two
  concurrent requests get chains offset by one instead of interleaving mid-chain. Fallback traffic is
  no longer counted against the rotation, so distribution across upstreams under partial failure
  shifts — evenly-loaded distribution (`tests/rpc_proxy.rs:36`) is unaffected.

## Logging

No new events and no schema change. The v0.1 schema in
[v0.1.md](v0.1.md#logging) stands as written. Two field semantics change, both from issue #2:

- `retries_exhausted.error` carries the full text of the last failure rather than a `&'static str`
  category, which is what the v0.1 spec already said it should be.
- `attempt_failed.error` carries the flattened `reqwest` source chain, because `Display` on the
  outer error stops at `error sending request` and drops the actual cause.

**The never-log-`rpc_url` rule applies with more force after this change.** Flattening a source chain
emits text the proxy did not author, and provider URLs embed the API key in the path. The flattening
is applied *after* `without_url()`; the remaining frames are transport-level and carry no path. Any
future widening of an error's text has to re-check that ordering.

`request_id`, span placement, and the `event`-as-a-field convention are untouched.

## Known Bugs

### Closed by this release

- **Retries can land on the upstream that just failed** (v0.1, Correctness). A chain of distinct
  upstreams removes the case entirely for `max_attempt <= upstream_count`, and makes it structurally
  impossible rather than merely unlikely.
- Everything specified in issue #2: startup lifecycle events (`upstream_skipped`, `startup_ready`,
  `startup_failed`, `server_stopped`), `.unwrap()` on bind and serve, `retries_exhausted.error`
  carrying a category instead of the failure text, and unhelpful `reqwest` error causes.

### Carried forward, still open

Restated rather than referenced, because a version pointer hides which entries are still live. Full
reasoning stays in [v0.1.md](v0.1.md#known-bugs).

**Correctness** — head divergence across upstreams at different chain heights; no retry
classification, so deterministic errors like `execution reverted` are retried across the chain;
JSON-RPC errors riding on HTTP 200 (rate limits as `-32005`) are undetectable under the
status-code-only rule; error responses always carry `id: null`; `eth_sendRawTransaction` retry is
unsafe; batch rejection is a transport-level `[` peek with no JSON-RPC error object.

**Observability** — no fleet-level view; no JSON-RPC method in logs; `duration_ms` excludes the
inbound body read; log volume is uncapped at four lines per request.

**Routing and health** — no health state, so a dead upstream is never removed from the rotation.
v0.1.2 narrows the cost (a dead upstream now burns one chain slot instead of repeat attempts) but
does not fix it. This is v0.2's entire subject.

**Timeouts and limits** — per-attempt timeout is a fixed 3s and wrong for heavy methods; no total
deadline; no inbound request timeout; no request body size cap; `Retry-After` response headers
ignored; no exponential backoff.

**Config and naming** — API keys live in YAML; the listener is hardcoded to `127.0.0.1`;
`retry_after` is a misleading name for a flat inter-attempt delay; a `reqwest::Client` per upstream
rather than one shared. The first two are v0.2's entry blockers named above.

### New in this release

- **`max_attempt` can be unreachable without warning**: configuring `max_attempt: 5` against three
  upstreams silently caps at three. Startup does not log the effective value, so the config lies to
  whoever reads it.
- **The observation sink is a no-op**: every attempt outcome is constructed and discarded. The
  `String` allocation per failed attempt is not new — #2 already made the error message owned, and
  only the log line reads it — so the outcome struct wraps what the hot path allocates anyway.
- **The log schema is still unasserted**: #5 routes tests through the real composition path, but no
  test calls `telemetry::init` — the writer is not injectable until #7 lands, so the release that
  reshapes the request path cannot prove it kept the log output byte-identical. Reviewers verify
  that by reading the diff.
