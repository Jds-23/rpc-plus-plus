## Problem

Currently the proxy service is stateless, so it relies on simple round robin handler. Simple round robin is inefficient.

## Goals

- **Healthy Based on Healthiness**: With state it can have handler based on healthyness or error rate. Also, we set a healthiness limit if a rpc drops certain healthiness we can temporary delist it.
- **Better Metrics For Prometheus**: We need to know more contrext on current state of the proxy service, like rpc healths. So that we can take action (replace dead ones; recharge one which limits exhausted).
- **Docker image + compose**: now needed to get details to decision of arch or debug stuff

## Not doing

- **Caching**: deferred. Comes once a request can be classified as returning an immutable or a mutable response.
- **Least-latency routing**: plain healtiness for now, latency will be figured i=out in later stage
- **Auth**
- **Batch handling**: error out for now with HTTP 400
- **Multichain**
- **In-flight dedup**
- **Hedging**
- **Reversing The Delisted Upstreams**
- **grafana dashboard**
- **load testing**

The Decider splits into two paths on different clocks. A background loop snapshots the metrics db,
scores every upstream, and publishes an ordered plan grouped into health bands; if scoring fails or
times out, the previous plan stays in force. Per request, the handler loads the current plan and
walks each band from a rotating cursor, producing a bounded fallback chain. Least-recently-used
ordering among equally-healthy upstreams is the cursor rotation — there is no last_used timestamp
in the metrics db, and the request path performs no writes to shared scoring state.
````
````

The practical upshot: the only per-request write left on the hot path is a relaxed `fetch_add` per band, and per-attempt writes go to a structure nothing is currently sorting against. The read-consistency problem the snapshot was solving stops being a hot-path concern at all, because the only reader is the background loop.


## Sharpest decision

- Every restart will behave as a cold process until it accumulates enough samples again. This also make load testing not possible. 
- Instead of getting Upstream on every retry, gxet an ordered list.
- Use snapshot of N secs instead getting fresh health mertic to calculate the list every time 

## Breaks when

- **One upstream fails below healthy limit**: On the first time, it falls to below limit, Log at `warn`, and add it to an exclusion list. Next time it will not be included in order list or considered. Until and unless it is removed from the exclusion list but will be handled by different service.
